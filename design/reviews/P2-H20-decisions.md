## 1. D-120 — เหตุปฏิเสธ `no_class` / `no_hp` ของ confirm

### 1.1 คำตัดสิน: ACCEPTED

### 1.2 เหตุผล

1. **`no_hp` เป็นข้อเท็จจริง ไม่ใช่ข้อผิดพลาด.** F06-R05 ให้เข้าได้เมื่อ HP > 0 การปฏิเสธตอน HP ≤ 0 จึงเป็นกฎที่ตั้งใจ `common.error` + `common.retry` สื่อว่า "ระบบพัง ลองใหม่อาจหาย" ซึ่งผิดความจริงและชวนกดซ้ำโดยไม่มีผล
2. **หลักการตัดสินข้อ 3 (ต้นทุนการเดินทางสูง บทลงโทษจึงต้องต่ำ).** ผู้เล่นที่เจอเหตุนี้เดินมาถึงขอบ dungeon แล้ว บรรทัด "HP หมด รอฟื้นก่อน หรือใช้ยาฟื้น" บอกทางกลับเข้าเล่นสองทางทันที (ฟื้นเริ่มทันทีตาม R04 และใช้ยานอก run ตาม R26) แทนที่จะปล่อยให้ยืนงงหน้าปุ่ม ตรงเจตนาข้อนี้มากกว่าของเดิม
3. **`no_class` ทางหลักไม่เปลี่ยน.** R29 บังคับเลือกพลังก่อนถึงแผนที่ เหตุนี้จึงเป็นทาง fail closed ที่ไม่ควรเกิด การเปิด `S-00-class-select` ทับทันทียังเป็นทางหลักตาม N-01 เดิม บรรทัดสำรองเป็นแค่ชั้นกันพลาดถ้า sheet ขึ้นไม่สำเร็จ ผู้เล่นจึงไม่ค้างที่ปุ่มกดไม่ได้โดยไม่รู้เหตุ
4. **ไม่แตะกฎของเกม.** ลำดับตรวจของ confirm (`run_active → no_class → no_hp → dungeon_closed → unsupported_mode →` 4 เหตุ GPS, D-114), R05, R29 และ Flow B/C ไม่เปลี่ยน เปลี่ยนเฉพาะสิ่งที่แสดงบนจอ check-in ไม่ใช่รางวัล จึงไม่มี movement gate มาเกี่ยว
5. **ยาฟื้นไม่อยู่ในรายการห้ามสอนใน 10 นาทีแรก** (ตลาด ตีบวก raid ลงแต้ม stat เปลี่ยน class party ละเอียด) และ `no_hp` แทบไม่เกิดใน 10 นาทีแรกอยู่แล้ว (R-P2-06: เลเวล 1 ถึง auto-retreat ราว 40–70 นาที และ auto-retreat ที่ 25% ทำให้ HP ไม่ถึง 0 ในค่าเริ่มต้น)

## 2. balance-model §21 — ย่านเปิดตัวบน client และ `{areaName}`

### 2.1 คำตัดสิน §21.3: เลือก (ข) — เลิกระบุชื่อเขตที่ผู้เล่นยืนอยู่

### 2.2 เหตุผล

1. **(ข) ต้องมีอยู่แล้วไม่ว่าเลือกทางไหน** (§21.4 ข้อ 2 ของ systems-designer): lookup ไม่เจอที่เส้นขอบ, โหลดไฟล์ไม่สำเร็จ, fallback R55 · การส่ง (ข) คือการส่งฐานที่ขาดไม่ได้ ส่วน (ก) เป็นส่วนเพิ่มล้วน
2. **ช่วงเวลาที่ (ก) คุ้มผ่านไปแล้ว.** §21.4 ข้อ 3 ให้ทำ (ก) ถ้า location-engineer มี 1 วันใน W6–W7 ตอนนี้คือ W7 และ F06-T09/T10 เริ่ม W9/W10 การเปิดงาน geometry 79 เขต + test + ชื่อแสดงผลตอนนี้เสี่ยงเลื่อน build ของ loop หลัก ซึ่งกระทบการออกไปเดินจริงมากกว่าข้อความในการ์ดรอง
3. **ย่านเปิดตัวยังไม่นิ่ง.** หลัง coverage rerun (P2-H11) ปทุมวันไม่ผ่าน G1 และบางรักไม่ผ่าน G2 เป็นคำถามค้างถึง HUMAN (working assumption: คง D-083) ถ้า launch-area เปลี่ยน ไฟล์ทุกเขตที่ต้องเป็น superset ของ launch-area (§21.4 ข้อ 4) ต้อง build ใหม่ (ข) ไม่ผูกกับผลนี้เลย

## 3A. A-P2-X31-1 — `temporarilyClosed` ระหว่าง onboarding แสดงเวลาของแห่งไหน (เพิ่มจาก orchestrator)

ที่มา: `docs/tech/F06-hp-damage-onboarding.md` 9.2 ข้อ 4 และรายการสมมติฐาน (P2-X31) · spec F06-R37 ข้อ 2 บอกแค่ "แสดงเวลาเปิดถัดไปของแห่งที่ครอบเลเวล" ไม่ระบุว่าแห่งใดเมื่อมีหลายแห่ง

### คำตัดสิน: ยืนยัน A-P2-X31-1 (พร้อมกฎเสริม 2 ข้อ)

กฎ (QA ทดสอบได้)
1. ระหว่าง onboarding เมื่อไม่มี dungeon ที่ครอบเลเวลเปิดอยู่เลย เป้าเดียวของจอ = dungeon ที่ครอบเลเวลที่**ใกล้สุด** (ระยะเส้นตรงถึงขอบก่อนปัด, F04-R35) ไม่ว่าจะเปิดเมื่อไร
2. เวลาเปิดถัดไป ระยะ ทิศ และปุ่มนำทาง ต้องชี้ dungeon เดียวกันเสมอ ห้ามแสดงเวลาของแห่งหนึ่งคู่กับทิศของอีกแห่ง
3. (เสริม) ระยะเท่ากันหลังคำนวณก่อนปัด → เลือกแห่งที่เปิดเร็วกว่า · ยังเท่ากันอีก → เรียงตาม `dungeon_id` เพื่อให้ผลคงที่ทุกครั้ง
4. (เสริม) ประเมินเป้าใหม่ตามจังหวะเดิมของ R50 (เปิดแอป และเมื่อตำแหน่งเปลี่ยนเกิน `config: unlocks.home.reevaluateDistance_m`) และเมื่อเป้าเดิมเปิดแล้ว (สถานะเปลี่ยนเป็น `far` หรือ `near` ตามปกติ) · ไม่สลับเป้าไปมาระหว่างนั้น
5. ไม่มี dungeon ใดครอบเลเวล 1 ใน artifact = บั๊กของข้อมูลตามที่ tech note เขียน ยืนยันด้วย · level-designer และ build dungeon ต้องตรวจว่าเลเวล 1 ถูกครอบเสมอ

เหตุผล
- จอที่เวลาพูดถึงที่หนึ่งแต่ลูกศรชี้อีกที่ ทำให้ผู้เล่นเดินไปแล้วเจอที่ปิด ขัดหลักการข้อ 3 (มาถึงแล้วต้องเล่นได้) · เป้าเดียวคือสิ่งที่ผู้เล่นเข้าใจได้โดยไม่ต้องอธิบาย ตรงเป้าหมายเดียวของนาที 1–3 ในตาราง "10 นาทีแรก" (เดินไปให้ถึง ไม่สอนอย่างอื่น)
- "เปิดเร็วสุด" อาจเป็นแห่งที่ไกลมาก ทำให้ต้นทุนเดินทางของคนใหม่สูงขึ้นในจังหวะที่ยังไม่ได้รางวัลก้อนแรก
- ความเสี่ยงที่รับไว้: แห่งใกล้สุดอาจเปิดอีกนาน ขณะที่แห่งที่ไกลกว่านิดเดียวเปิดเร็วกว่ามาก · ใน Phase 2 dungeon นำร่องอยู่ใน 3 เขตและเป็นสวน/ตลาดที่เวลาทำการใกล้กัน โอกาสเกิดต่ำ · ถ้า playtest หรือ QA เจอจริง ให้ส่ง game-director พิจารณากฎ "เวลาถึงที่เปิดได้เร็วสุด" ใน Phase 3 ไม่แก้ใน Phase 2

ผลต่อเอกสาร: tech note เขียนตรงแล้ว ไม่ต้องแก้ · spec F06-R37 ข้อ 2 ต้องเติมกฎข้อ 1–3 (งานของ game-director ในรอบแก้ spec ถัดไป ดู handoff ถึง producer) · uiux ตรวจว่า flow F06 A7/F1 เขียนเป้าเดียวตรงกัน
