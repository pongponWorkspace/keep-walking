# เกณฑ์ให้คะแนนย่านเปิดตัว (Launch Criteria)

Task: P1-F01-T02 · เจ้าของ: level-designer · สถานะ: DRAFT พร้อมให้ P1-F01-T06 (นับรายเขต + heatmap) และ P1-F01-T07 (coverage report) ใช้
อ้างอิง: `product/prd/F01-coverage-survey.md` (หัวข้อ 3–5, cross-read PM-S07) · `tools/coverage/METHOD.md` (โครงสร้าง candidates, `rep_point`) · `design/levels/dungeon-rules.md` (นิยาม dungeon ที่ใช้ได้) · GDD "กลยุทธ์การเปิด", "10 นาทีแรกของคนใหม่"

หลักการ: เอกสารนี้ **ไม่สร้างเกณฑ์ Go/No-go ใหม่** (นั่นคือ PRD F01 หัวข้อ 4 ที่ product-manager เป็นเจ้าของ) แต่สร้าง **เครื่องมือจัดอันดับ** ว่า 79 เขต/อำเภอไหนน่าเป็น "ย่านเปิดตัว 2–3 ย่าน" ที่ P1-F01-T07 จะเอาไปตรวจกับเกณฑ์ PRD อีกที หน่วยวัดทุกตัวในเอกสารนี้ใช้นิยามเดียวกับ PRD F01 หัวข้อ 3 ทุกตัว (ห้ามมีหน่วยที่สอง)

## 1. นิยาม "ย่าน" (ต้องตรงกับ location-engineer และ PRD)

**ย่าน = เขต (กรุงเทพฯ) หรือ อำเภอ (5 จังหวัดปริมณฑล)** ตาม `tools/coverage/METHOD.md` หัวข้อ 2 (relation `admin_level=6`) และ PRD F01 หัวข้อ 3 — ไม่ใช่ grid ที่ตั้งเอง เพื่อให้อ้างอิงข้อมูลประชากรและเขตปกครองที่ทางการเผยแพร่ได้ตรงกัน

- ใช้ `district_osm_id` เป็นตัวระบุย่าน ไม่ใช้ชื่อ (ชื่อซ้ำข้ามจังหวัดได้ตาม METHOD 9.3)
- candidate ที่มี `multi_district = true` (คร่อมสองเขต) นับเข้า**ทั้งสองย่าน**สำหรับตัวชี้วัดจำนวน/ความหนาแน่น แต่ประชากรที่อยู่ในโซนเขียวของ candidate นั้นคำนวณแยกตามสัดส่วนพื้นที่ที่ทับแต่ละเขต (location-engineer เป็นผู้คำนวณจริงใน T06 เอกสารนี้กำหนดหลักการเท่านั้น)
- รวม 79 ย่านตาม METHOD หัวข้อ 2 (กรุงเทพฯ 50 เขต + ปริมณฑล 29 อำเภอ)

## 2. หน่วยวัดร่วม (อ้างจาก PRD F01 หัวข้อ 3 ทุกตัว — ไม่เขียนนิยามซ้ำสองที่)

| หน่วยวัด | นิยาม (อ้าง PRD F01 หัวข้อ 3) |
| --- | --- |
| ระยะจาก dungeon ใกล้สุด | ระยะเดินตามโครงข่ายถนน/ทางเท้าโดยประมาณ = ระยะเส้นตรงจาก `rep_point` (METHOD 9.1/README 5) × route factor ที่ระบุแหล่งที่มาไว้ชัดเจน (PRD หัวข้อ 8 เสนอ 1.3–1.4 เท่าสำหรับพื้นที่เมือง เป็นค่าเริ่มต้นถ้ายังไม่มี routing engine) |
| dungeon ที่ใช้ได้ (valid) | ผ่านทุกกฎใน `dungeon-rules.md` และ `tools/coverage/METHOD.md`: tag 6 ชุด, `area.minArea_m2 ≤ area_m2 ≤ area.maxArea_m2`, ไม่ติด blocklist, ไม่ติด `review_required` ที่ยังไม่ผ่าน HUMAN |
| โซนระยะทาง (เขียว/เหลือง/แดง) | ตามตาราง PRD F01 หัวข้อ 3 (เขียว ≤ 800 ม., เหลือง 800–3,000 ม., แดง > 3,000 ม. หรือไม่มี dungeon ในย่าน) |

| preset | ตาม `dungeon-rules.md` หัวข้อ 12 (สวนใหญ่ / ตลาด / สวนหย่อม เป็นหลัก, ริมน้ำ/ริมคลองเป็นชั้นที่สอง) |

## 3. สูตรให้คะแนนย่าน (Launch Score)

ใช้จัดอันดับ 79 ย่านเพื่อเลือกย่านที่น่าพิจารณาก่อนส่งเข้าตรวจเกณฑ์ Go/No-go ของ PRD (หัวข้อ 4.1–4.3) **ไม่ใช่ตัวตัดสิน Go/No-go เอง** — คะแนนนี้เป็นเครื่องมือช่วยเรียงลำดับความสำคัญตอนเขียน coverage report (P1-F01-T07) เท่านั้น น้ำหนักด้านล่างเป็นค่าที่ level-designer กำหนดเอง (ไม่ใช่ค่าเกม balance ที่ต้องอยู่ใน `config/balance/`) เพราะเป็นเครื่องมือวิเคราะห์ใช้ครั้งเดียวของ T06/T07 ไม่ใช่ค่าที่ runtime ของเกมอ่าน — ถ้า location-engineer จะใช้ซ้ำในสคริปต์ ให้ย้ายน้ำหนักเหล่านี้ไปเป็นไฟล์ `tools/coverage/analysis/launch-score.config.json` แทนการฝังในโค้ด (ตามหลัก "ไม่มี magic number ในสคริปต์" ของ METHOD หัวข้อ 1)

```
LaunchScore(ย่าน) =
    0.25 × densityScore
  + 0.25 × walkDistanceScore
  + 0.20 × transitAccessScore
  + 0.15 × presetDiversityScore
  + 0.15 × populationDensityScore
```

ทุก sub-score normalize เป็น 0–1 ด้วย min-max ข้าม 79 ย่าน (ย่านที่ดีที่สุดของตัวชี้วัดนั้นได้ 1.0 แย่ที่สุดได้ 0) เพื่อให้เทียบข้ามหน่วยกันได้ คำนวณเฉพาะย่านที่มี valid dungeon อย่างน้อย 1 แห่ง ย่านที่ไม่มีเลยได้ `LaunchScore = 0` ทันที (ไม่ normalize ให้)

## 4. นิยามแต่ละ sub-score (5 ตัวชี้วัดตามที่ board กำหนดไว้ครบ)

### 4.1 `densityScore` — จำนวน dungeon ที่ใช้ได้ต่อตร.กม.

```
rawDensity(ย่าน) = จำนวน valid dungeon ในย่าน ÷ พื้นที่ย่าน (ตร.กม.)
densityScore = minMaxNormalize(rawDensity ข้าม 79 ย่าน)
```

ใช้ต่อตร.กม.แทนจำนวนดิบ เพื่อไม่ให้ย่านที่กว้างมาก (เช่น อำเภอชานเมืองของนครปฐม) ได้เปรียบย่านที่แน่นแต่เล็กกว่าอย่างไม่เป็นธรรม — สอดคล้องกับ GDD "กลยุทธ์การเปิด" ที่ต้องการย่านที่ "dungeon หนาแน่น" ไม่ใช่ย่านที่มีจำนวนรวมมากเพราะพื้นที่ใหญ่

### 4.2 `walkDistanceScore` — ระยะเดินเฉลี่ยถึง dungeon ใกล้สุด

```
avgWalkDistance(ย่าน) = ค่าเฉลี่ยถ่วงน้ำหนักด้วยประชากรของระยะเดิน (หัวข้อ 2) จากทุกจุดตัวแทนประชากรในย่าน
                         ไปยัง valid dungeon ที่ใกล้ที่สุด (ไม่จำกัดว่าต้องอยู่ในย่านเดียวกัน — คนที่บ้านติดขอบเขตอาจใกล้ dungeon ย่านข้างๆ กว่า)
walkDistanceScore = minMaxNormalize(−avgWalkDistance ข้าม 79 ย่าน)  // ยิ่งใกล้ยิ่งได้คะแนนสูง
```

ใช้ตารางประชากรระดับกริดของ WorldPop (100 ม./ช่อง) เป็นจุดตัวแทนแทนจุดศูนย์กลางย่านเดียว เพื่อให้ค่าเฉลี่ยสะท้อนการกระจายตัวจริงของคน ไม่ใช่แค่ระยะจากศูนย์กลางเขตซึ่งอาจไม่มีคนอยู่จริง (location-engineer พิจารณาความเป็นไปได้ทางเทคนิคใน T06 ถ้าทำเต็มรูปแบบไม่ทันเวลา ให้ใช้ค่าเฉลี่ยแบบไม่ถ่วงน้ำหนักของกริดที่มีประชากร > 0 แทน และบันทึกไว้ใน `district-counts.csv`)

### 4.3 `transitAccessScore` — ระยะเดินจากสถานีรถไฟฟ้า/ป้ายรถเมล์ ถ่วงน้ำหนักมากกว่าที่จอดรถ (N-6)

**หลักการ:** เกมนี้ให้รางวัลกับการเดินจริง ย่านที่เข้าถึง dungeon ได้ด้วยขนส่งสาธารณะ (เดินต่อจากลงรถไฟฟ้า/รถเมล์) ควรได้คะแนนสูงกว่าย่านที่เข้าถึงได้จริงเฉพาะคนขับรถมาจอด เพราะสอดคล้องกับกลุ่มผู้เล่นเป้าหมายและ pillar "เดินจริง" มากกว่า — **ที่จอดรถไม่ได้ให้คะแนนบวกในสูตรนี้เลย** ใช้เป็นข้อมูลประกอบเชิงคุณภาพใน coverage report เท่านั้น (ตาม N-6 "ให้น้ำหนักระยะเดินจากรถไฟฟ้า/ป้ายรถเมล์มากกว่าที่จอดรถ")

```
railWalkDistance(dungeon) = ระยะเดิน (หัวข้อ 2) จาก dungeon ถึงสถานีรถไฟฟ้า/รถไฟที่ใกล้ที่สุด
                             (OSM: railway=station, station=subway|light_rail|train, public_transport=station)
busWalkDistance(dungeon)  = ระยะเดิน จาก dungeon ถึงป้ายรถเมล์ที่ใกล้ที่สุด (OSM: highway=bus_stop, amenity=bus_station)
transitDistance(dungeon)  = ถ้ามีสถานีรถไฟฟ้าในระยะที่ยอมรับได้: (2 × railWalkDistance + 1 × busWalkDistance) / 3
                             ถ้าไม่มีสถานีรถไฟฟ้าในระยะที่ยอมรับได้: ใช้ busWalkDistance อย่างเดียว
transitAccessScore(ย่าน)  = minMaxNormalize(−ค่าเฉลี่ย transitDistance ของ valid dungeon ทุกแห่งในย่าน ข้าม 79 ย่าน)
```

น้ำหนัก 2:1 ระหว่างรถไฟฟ้ากับรถเมล์เป็นการเลือกของ level-designer (ไม่ใช่ตัวเลขจาก GDD) เหตุผล: รถไฟฟ้าตรงเวลาและจูงใจให้เดินทางไกลข้ามย่านได้มากกว่ารถเมล์ที่ตารางเวลาไม่แน่นอน จึงมีผลต่อ "การเดินทางมาเล่นครั้งแรก" มากกว่า — **handoff ถึง location-engineer:** `tools/coverage/pipeline` ปัจจุบัน (README หัวข้อ 4/5) ยังไม่ดึง tag `railway=station`/`public_transport=station`/`highway=bus_stop` เข้า `KeyFilter` ต้องเพิ่มเป็นงานของ T06 (ไม่ใช่ T05 ซึ่งปิดขอบเขตแค่ 6 ชุด tag ของ dungeon และ blocklist แล้ว)

### 4.4 `presetDiversityScore` — ความหลากหลายของ preset

```
presetDiversityScore(ย่าน) = (จำนวน preset หลักที่มีตัวแทนอย่างน้อย 1 แห่ง ใน {สวนใหญ่, ตลาด, สวนหย่อม}) ÷ 3
```

ตรงกับหน่วยของ G3/S3 ใน PRD ทุกประการ (ไม่ต้อง normalize เพิ่มเพราะเป็นสัดส่วน 0–1 อยู่แล้ว) preset ชั้นที่สอง (ริมน้ำ/ริมคลอง) ไม่นับในตัวหารนี้ ตรงกับที่ PRD หัวข้อ 5 ถ่วงน้ำหนักทางเสริมแยกต่างหากจาก dungeon หลัก

### 4.5 `populationDensityScore` — ความหนาแน่นประชากร

```
populationDensityScore(ย่าน) = minMaxNormalize(ประชากรย่าน ÷ พื้นที่ย่าน (ตร.กม.) ข้าม 79 ย่าน)
```

น้ำหนักน้อยกว่าตัวชี้วัดการเข้าถึง (4.1–4.3) โดยตั้งใจ: ความหนาแน่นสูงอย่างเดียวไม่มีประโยชน์ถ้าคนเดินไป dungeon ไม่ถึง (นั่นคือเหตุผลที่ `walkDistanceScore` มีน้ำหนักมากกว่า) แต่ยังมีน้ำหนักอยู่บ้างเพราะ GDD "กลยุทธ์การเปิด" ต้องการย่านที่ "มีคนเล่นในย่านเดียวกัน" มากพอให้ Nearby Party ทำงาน ซึ่งขึ้นกับจำนวนคนจริงในพื้นที่ ไม่ใช่แค่ระยะเดิน

## 5. วิธีใช้คะแนนนี้ใน T06/T07 (ไม่ทดแทนเกณฑ์ PRD)

1. P1-F01-T06 คำนวณทั้ง 5 sub-score และ `LaunchScore` ต่อ 79 ย่าน ใส่ใน `district-counts.csv` เป็นคอลัมน์เพิ่มเติม (ไม่ใช่แทนที่คอลัมน์ดิบตามหัวข้อ acceptance ของ T06)
2. P1-F01-T07 เรียง `LaunchScore` จากมากไปน้อย เลือก **5–8 ย่านบนสุด** มาตรวจกับเกณฑ์ตัวเลขจริงของ PRD F01 หัวข้อ 4 (G1–G4 / S1–S4) ทีละย่าน — `LaunchScore` สูงไม่รับประกันว่าจะผ่าน Go เพราะ PRD ใช้ค่าขั้นต่ำแบบ all-or-nothing ต่อเกณฑ์ (เช่น G2 ต้องการ ≥10 แห่งแน่นอน ไม่ใช่คะแนนเฉลี่ย) ส่วน `LaunchScore` ช่วยจัดลำดับว่าควรเริ่มตรวจย่านไหนก่อนเพื่อประหยัดเวลา ไม่ต้องไล่ตรวจทั้ง 79 ย่านด้วยมือ
3. ย่านที่คะแนนสูงแต่ไม่ผ่าน G-เกณฑ์ให้ไปดูเกณฑ์ S (Go พร้อมทางเสริม) ต่อ ตามลำดับความสำคัญของทางเสริมใน PRD หัวข้อ 5.4 (ชั้นที่สอง > ชั่วคราว > ผู้เล่นเสนอ)
4. coverage report (T07) ต้องแสดงตาราง 5 sub-score + `LaunchScore` ของย่านที่แนะนำทุกย่าน เพื่อให้ HUMAN (P1-F01-T11) เห็นเหตุผลเชิงตัวเลขของการจัดลำดับ ไม่ใช่แค่ผลผ่าน/ไม่ผ่าน

## 6. `verification_mode` และ `floor_level` (v1)

ทุก candidate ที่ใช้คำนวณคะแนนในเอกสารนี้ต้องมี `verification_mode = "continuous_gps"` และ `floor_level = null` ตามที่ `config/balance/dungeons.json#verification` กำหนด และตามที่ `design/levels/dungeon-rules.md` หัวข้อ 13 อธิบายไว้แล้ว — เอกสารนี้ไม่ให้คะแนนหรือถ่วงน้ำหนักพิเศษกับ candidate ในอาคาร เพราะ v1 ไม่มี candidate ประเภทนั้นอยู่แล้ว (non-negotiable ข้อ 5 ของ CLAUDE.md)

## 7. ข้อจำกัดของคะแนนนี้

- ต้องมี candidate ผ่าน T05 ครบก่อนจึงคำนวณได้จริง (เอกสารนี้เขียนก่อนเห็นข้อมูล ตามลำดับเวลาเดียวกับ PRD F01 ที่เขียนก่อนเห็น `candidates.geojson`)
- `walkDistanceScore` และ `transitAccessScore` ต้องพึ่ง route factor ประมาณการ (หัวข้อ 2) จนกว่าจะมี routing engine จริง — ถ้า route factor เปลี่ยนภายหลัง คะแนนของทุกย่านเปลี่ยนตามสัดส่วนเดียวกัน (ไม่กระทบการจัดอันดับสัมพัทธ์มากนัก เพราะ min-max normalize คงทนต่อการคูณด้วยค่าคงที่เดียวกันทุกย่าน)
- น้ำหนัก 0.25/0.25/0.20/0.15/0.15 และน้ำหนักย่อย 2:1 ของ transit เป็นดุลยพินิจของ level-designer ไม่ใช่ตัวเลขจาก GDD — ถ้า design gate (P1-F01-T09) เห็นว่าน้ำหนักผิดสัดส่วน ให้แก้ในเอกสารนี้ได้ก่อนที่ T07 จะใช้จัดอันดับจริง (หลักการเดียวกับ PRD หัวข้อ 8: ห้ามแก้เกณฑ์หลังเห็นผลจริงแล้ว)
