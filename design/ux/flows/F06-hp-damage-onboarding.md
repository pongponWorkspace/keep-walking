## 2. Flow A — Onboarding นาที 0–10 (F06-R36..R43, ตาราง 3.8 ของสเปก)

state machine อ้างอิง (สเปกหัวข้อ 4): `O-intro` → `O-age` → (`O-underage` จบ) / `O-consent` → `O-permission` → `O-map` → `O-class` → `O-nearest` (ใกล้) หรือ `O-home` (ไกล/นอกพื้นที่/ไม่รู้ตำแหน่ง) → `O-first-run` → `O-done` — เก็บใน `kw.p2.*` เป็นขั้นที่ผ่านแล้ว เปิดแอปใหม่กลางทางกลับไปขั้นแรกที่ยังไม่ผ่าน (F06-R36, H-E18)

A1. **`S-00-intro`** — ข้อความเดียว `[onboarding.intro]` ("กรุงเทพฯ กำลังมีปัญหา") ไม่มีปุ่มข้าม กดที่ใดก็ได้ทั้งจอเพื่อไปต่อ (ปุ่มเดียวเต็มจอ) → `S-00-age-gate` (**ไม่ใช่ consent ตำแหน่งตามที่ F03 เขียนไว้เดิม — ดูหมายเหตุ override ข้อ 1**)

A2. **`S-00-age-gate`** — หัวจอ `[age.gateTitle]` ("ยืนยันอายุ") + `[age.gateBody]` ("เกมนี้สำหรับอายุ {minAge} ปีขึ้นไป เลือกปีเกิดแล้วกดยืนยัน") ตัวเลือกปีเกิดจากรายการ `[age.gateOptions]` (ไม่พิมพ์) + ปุ่มยืนยันแยก `[age.gateConfirm]` (`.btn-disabled` จนกว่าจะเลือกตัวเลือก) — เกณฑ์ผ่าน/ไม่ผ่านคำนวณจาก `config: privacy.minAge_yr` แบบ `minAgeComparison` เก็บในเครื่องเฉพาะธง "ผ่านแล้ว" ไม่เก็บปีเกิดหรือช่วงอายุ (F06-R45)
   ⤷ เงื่อนไข: ผ่านเกณฑ์ → `S-00-consent-location`

   ⤷ เงื่อนไข: tick แรกไม่ผ่าน gate (H-E20) → `[run.tickDenied]` ตามปกติ (flow F05 A3) **ไม่มีทางลัดของ onboarding** รอ tick ถัดไป — เกิดขึ้นได้และไม่ใช่บั๊ก
   ⤷ เงื่อนไข: **tick ก้อนแรกมาจาก tick บางส่วนของ D-059 (ปิด dungeon กลาง run แรก, แก้ O-3 ของ `design/reviews/F04-F05-design-gate.md` — รายละเอียดเต็มอยู่ flow F05 หัวข้อ 2 ข้อ A2b)** → **ไม่แสดง toast ของ A2 เลย** เพราะ `dungeon_exited` เกิดพร้อมกัน จอสลับไป `S-04-run-summary` ทันที ก้อนแรกนี้สื่อสารผ่านหน้าสรุปเท่านั้น (แถวของ/exp/จำนวน tick ปกติ ไม่มี badge "ก้อนแรก" แยก) ปุ่มเดียวคือ `[run.summaryContinue]` ซึ่งใช้วลีเต็มเดียวกับ `[run.continueCta]` ตาม D-050 — **onboarding ยังจบที่จังหวะนี้เหมือนเดิม** (`O-done` ตั้งจาก `firstEver`/ธง `first_reward` ของ tick นั้น ไม่ใช่จากการเห็น toast) ไม่ใช่ทางให้รางวัลที่สองหรือ code path แยก (GD B-07)

## 4. Flow C — HP, การตี, แจ้ง 30%, auto-retreat, ตาย, ฟื้น (F06-R01..R28, R-B1)

ที่มา: การตีเป็นการคำนวณล้วนของ engine (`resolveHit`, ไม่มี combat log ให้ผู้เล่นเห็น) — จอผู้เล่นแสดงแค่ **ผล** ของลำดับ R-B1 (flow F05 หัวข้อ 2 A5 ยืนยันลำดับ tick ก่อน hit อีกครั้ง) ไม่มีจอ "กำลังต่อสู้" ใดๆ ทั้งสิ้น

### 4.1 HP bar (ถาวรบน `S-03-run` ทุกสถานะ รวมจอพกกระเป๋า)

C1. HP bar (`.hp-track`/`.hp-fill` เดิมจาก style.css + เส้นแบ่งขอบ `components.md` 13.6) แสดงค่าจาก engine เท่านั้น (client ห้ามคำนวณเอง, F06-R11) ต่อเนื่องข้าม run (F06-R02) — **onboarding รอบแรกไม่มี tooltip อธิบาย HP bar** (F06-R41, ตรงกับ N-3 ของ F04-flow-approval — บทเรียนเดียวคือ `dungeon.confirmTutorialLine` เท่านั้น)

C2. **แจ้ง HP ต่ำ (H1, F06-R14)**: HP ก่อน hit > `config: dungeons.hpSafety.lowHpWarningThreshold_pct` และ HP สุดท้ายหลังยา ≤ เส้นนั้น → สั่น (ถ้าเครื่องรองรับ) + เสียง + toast `[run.hpLow]` ("HP ต่ำ กลับบ้าน ซื้อยา หาเพื่อนที่มี Support หรือไม่ก็เลิกดื้อ" — ข้อความ canon ตรงตัวห้ามแก้) ครั้งเดียวต่อการลงผ่านเส้น ติดอาวุธใหม่เมื่อ HP ขึ้นเหนือเส้นอีกครั้ง (ยา, Support heal) **ไม่แจ้งตอนเข้า run ที่ HP ต่ำกว่าเส้นอยู่แล้ว** (บอกไว้แล้วที่ popup confirm A8/`dungeon.confirmLowHpNote`) **ไม่แจ้งตอนตาย** (ลำดับ R14 ก่อน R23 เสมอ hit ที่พา HP ถึง 0 ไม่ทริกเกอร์บรรทัดนี้ซ้ำ) — บนจอพกกระเป๋าใช้ fire-together ชุดเดียวกันโดยไม่ต้องออกจากจอมืด (components.md 12.1)
   ⤷ เงื่อนไข: เครื่องไม่รองรับ `navigator.vibrate` (iOS บนเว็บ) → ใช้เสียง + ภาพแทน **ห้ามแก้ด้วยการลดเกณฑ์หรือปิด auto-retreat** (F06-R15, pillars Q5/NN-8) — รายละเอียด fallback ของเสียงเป็นของ `audio/cue-list.md` (P2-F06-T13)
   ⤷ **แก้ P2-H39 (ปิดข้อขัดแย้งระหว่าง components.md 12.1 เดิมกับ `tokens.json#zIndex`):** ขณะจอพกกระเป๋าเปิดอยู่ (หัวข้อ 6 ของเอกสารนี้ Flow E) **`run.hpLow` ไม่แสดง `.toast` ที่มองเห็นเลย** เพราะ `.pocket-screen` อยู่ระดับ `overlay` (50) ทับ `.toast` (30) เสมอตามสเกล z-index (`components.md` หัวข้อ 15.1/15.4) — นี่เป็นกฎที่ตั้งใจ ไม่ใช่บั๊ก: จอพกกระเป๋าหมายถึงมือถืออยู่ในกระเป๋าจริง มองจอไม่เห็นอยู่แล้วไม่ว่า toast จะอยู่ชั้นไหน ช่องทางที่ผู้เล่นรับรู้ได้จริงบนจอนี้มีแค่ 3 อย่างเสมอ: (1) เสียง cue ของ `run.hpLow`, (2) สั่นตามเงื่อนไขข้างต้น, (3) ตัวเลข `[run.pocketHp]` บนจอพกกระเป๋าเองที่ลดลงให้เห็นทันทีที่หยิบมือถือขึ้นมาดู (ค่าจาก server เดียวกับ HP bar ปกติ, F06-R11) — ไม่มีทางที่สี่ ไม่ต้องมี toast ซ้อนที่มองไม่เห็นอยู่ดี (ดูเหตุผลเต็มที่ `components.md` หัวข้อ 15.4)

C3. **ยาอัตโนมัติ (F06-R12)**: HP หลัง hit ต่ำกว่า `config: economy.autoPotion.defaultThreshold_pct` และมียา (ถุงของ run ก่อน แล้วค่อย inventory) → ดื่มให้เองหนึ่งขวดต่อ hit ผู้เล่นเห็นแค่ toast สั้น `[run.autoPotionUsed]` ("ใช้ยาอัตโนมัติ") HP bar ขยับขึ้นให้เห็นเอง **ไม่มี popup ถามยืนยันก่อนใช้** (ตั้งใจให้ automatic จริง ไม่ขวางจังหวะเดิน) — **Phase 2 ไม่มีทางปรับเกณฑ์หรือปิดยาอัตโนมัติ** (ดูหมายเหตุ override ข้อ 5 และหัวข้อ 5 ของเอกสารนี้)

### 4.2 Auto-retreat (H2, F06-R16..R21)

C4. เปิดอยู่ (ค่าเริ่มต้น) และ HP สุดท้ายหลัง hit ≤ `config: dungeons.hpSafety.autoRetreatThreshold_pct` → run จบทันทีด้วย `exit_reason: auto_retreat` เก็บของครบ (F05-R21) — สัญญาณตอนเกิดเหตุ (ครั้งเดียว ชั่วคราว): overlay/effect สั้น `icon.ui.retreat` (art brief 3.8: "ไม่มีภาพความพ่ายแพ้") แล้วสลับไปหน้าสรุปทันที **ถ้าเกิดพร้อมเงื่อนไขแจ้ง 30% ในจังหวะเดียวกัน ผู้เล่นเห็น/ได้ยินสัญญาณเดียวคือ auto-retreat เท่านั้น** (F06-R16, F05-R18 ข้อ 5 — ไม่ใช่สั่นสองครั้งซ้อนกัน)
   **แก้ B-01 (canon ต้องอยู่บนจอที่ดูได้ทุกเมื่อ ไม่ใช่แค่ overlay ชั่วคราว):** หน้าสรุป (`S-04-run-summary`) แสดงหัวข้อ `[run.summary.autoRetreated]` ("ถอยอัตโนมัติ ของอยู่ครบ" — F04 flow หัวข้อ 7 เป็นเจ้าของหัวข้อนี้) **ต่อด้วยบรรทัดแรกใต้หัวข้อเป็นข้อความ canon เต็มของ GDD `[run.autoRetreat]`** ("HP เหลือต่ำกว่า {autoRetreatPct}% ระบบพาคุณกลับก่อน คุณรอด มอนสเตอร์ไม่ได้ แต่ก็ช่างมันเถอะ" — ห้ามแก้คำ) แล้วตามด้วยรายการของครบตาม F05 B1/B5 — คนที่หยิบมือถือขึ้นมาดูตอนไหนก็ได้หลังเหตุการณ์ (ไม่ใช่แค่ตอน overlay ยังค้างอยู่) ต้องเห็นข้อความ canon นี้ · ไม่เปลี่ยนหัวข้อจอเป็น `run.autoRetreat` (คงหัวข้อสั้น `run.summary.autoRetreated` ของ F04 ไว้ตามเดิม กันผลกระทบต่อ F04-04) — รายละเอียดตำแหน่งเต็มอยู่ flow F05 หัวข้อ 3 ข้อ B5 (แก้ใหม่ในรอบนี้ด้วย) และ wireframe `F04-04-run-state-summary.html`/`F05-02-run-summary-detail.html`

## 10. แอปถูกย่อ/ปิด และเน็ตหลุด

- **HP ฟื้น (นอก run) คำนวณจากเวลาที่ผ่านไปตามนาฬิกาของ host รวมช่วงที่แอปปิด** (F06-R04) — ปิดแอปตอน Recovering แล้วเปิดใหม่ 20 นาทีให้หลัง เห็น HP ฟื้นมาตามสัดส่วนเวลาจริงทันที ไม่ต้องรอ "จับเวลาสด" ระหว่างแอปเปิด
- **นาฬิกาเครื่องถูกตั้งย้อน**: HP ไม่ลดจากเหตุนี้ และตั้งจุดเริ่มนับฟื้นใหม่ที่เวลาปัจจุบัน (F06-R04) — เหมือนกฎ `clock_invalid` ของ F04 ที่ใช้กับ run
- **onboarding ถูกปิดแอปกลางทาง** (H-E18, ครอบคลุมในหมายเหตุ override ข้อ 1 + Flow A): เปิดใหม่กลับไปขั้นแรกที่ยังไม่ผ่านเสมอ ไม่เริ่มใหม่ทั้งหมด ยกเว้นกดปุ่ม "ลบข้อมูลในเครื่อง" (Flow G ข้อ G4) โดยตั้งใจ
- **เน็ตหลุดระหว่างจอ F06 ใดๆ**: ไม่มีผลใด (Phase 2 ไม่มี server, engine ในเครื่องล้วน) ยกเว้นการส่ง "ลงทะเบียนความสนใจ" ที่ยังค้าง `interest.pending` จนกว่าจะมี backend จริงใน Phase 3 (F23) — ไม่บล็อกการกดยืนยันในเครื่อง

### 18.1 ขั้นตอนที่คาดหวังสำหรับจอ `S-00-permission-browser` (handoff gameplay-programmer, ไม่ blocking ด้าน PDPA)

ลำดับที่ควรเป็นหลังแก้ (ต่างจากปัจจุบันที่ `acceptConsent()` เรียก `startLocationProvider()` ทันที):
1. ผู้เล่นกด `[consent.locationAccept]` บน `S-00-consent-location` → เขียน `kw.p2.consent = granted` เหมือนเดิม **แต่ยังไม่เรียก `startLocationProvider()`**
2. `currentOnboardingStep()` คำนวณได้ `'permission'` อยู่แล้วตามโค้ดปัจจุบัน (เงื่อนไข `locationConsent === 'granted' && permissionGranted === null`) — แค่เพิ่มกิ่ง render ใน `f04-app.ts` ให้จอ `S-00-permission-browser` (ใหม่ ทรงเดียวกับ `consent-location-screen.ts`) แสดงตอนนี้แทนที่จะปล่อยผ่านไม่มีจอ
3. ผู้เล่นกด `[consent.browserPrimingContinue]` ("ไปต่อ") → ตอนนี้เท่านั้นที่เรียก `startLocationProvider()` + เริ่ม `resolvePermission()` (ย้ายสองบรรทัดนี้จาก `acceptConsent()` ไปเมธอดใหม่ เช่น `confirmBrowserPriming()`)
4. permission จริงจาก OS มาแล้ว (`permissionGranted` ไม่เป็น `null` อีกต่อไป) → step กลับไปเป็น `'map'`/`'class'` ตามปกติ ไม่ต้องแก้ตรงนี้
5. telemetry `permission_browser_shown` ยิงตอนจอนี้ mount ครั้งแรก (แพทเทิร์นเดียวกับ `markConsentShown`/`markAgeGateShown` ที่มีอยู่แล้ว) — ยังไม่มีเมธอดนี้ในโค้ดปัจจุบัน ต้องเพิ่ม
6. ผู้เล่นกลับมาเปิดแอปใหม่ (returning player, `locationConsent` เดิม `granted` จาก session ก่อน) **ไม่เห็นจอนี้ซ้ำ** เพราะ onboarding ผ่าน `'done'` ไปแล้ว (`classChosen`/`firstRunEntered`/`firstRewardDone` ล้วน `true`) `currentOnboardingStep()` ไม่มีทางคืน `'permission'` ให้คนกลุ่มนี้อีก (ตรวจแล้วจากโค้ด onboarding-step.ts) ไม่ต้องกังวลเรื่อง regression

### 20.3 C6-07 — บรรทัดสรุป run ที่ผ่านมา: หัวข้อ + เวลา + ชื่อ

ตรวจโค้ดจริง (`f04-app.ts` ที่ `onOpenRecentRuns`, `ui/run-state-view.ts#runSummaryHeaderKey`, `dungeons/open-time.ts#formatOpenTime`, `copy/names.ts#getDungeonShortName`/`isResolvedDungeonName`) ก่อนตัดสิน — ทุกชิ้นที่ต้องใช้มีอยู่แล้วในโค้ดยกเว้นตัวจัดรูปแบบเวลาในอดีต

1. **หัวข้อ (ปิด "which `run.summary.*` title key per exit reason"):** ใช้ `runSummaryHeaderKey(summary.exitReason)` ตัวเดิมที่ `ui/run-state-view.ts` export ไว้แล้วสำหรับหัวหน้าสรุป run (F04 flow หัวข้อ 7) ตรงๆ **ไม่มี key ใหม่ ไม่มี mapping คู่ขนานชุดที่สอง** — บรรทัดที่บ้านกับหัวหน้าสรุป run ใช้ประโยคเดียวกันเป๊ะ (ไม่เสี่ยงคำสองชุดไม่ตรงกันในอนาคต)
2. **เวลา (ปิด "past-time format today / yesterday / older"):** `formatOpenTime` (เดิม) มองไปข้างหน้าเท่านั้น (`dayDiff <= 0` ยุบเป็น `unit.today` เสมอ — ผิดสำหรับเวลาในอดีต) เพิ่มฟังก์ชันใหม่ **`formatPastTime(pastMs, nowMs, utcOffsetMin)`** ไว้ข้าง `formatOpenTime` ในไฟล์เดียวกัน (`dungeons/open-time.ts`) reuse helper private เดิมทั้งหมด (`localDayIndex`, `localWeekdayIndex`, `localClockText`, `WEEKDAY_KEYS`) ไม่มีของใหม่ที่ต้อง export เพิ่ม:
   - `dayDiff = localDayIndex(nowMs) - localDayIndex(pastMs)` (สลับเครื่องหมายจาก `formatOpenTime` เพราะทิศทางกลับกัน)
   - `dayDiff <= 0` (วันเดียวกัน หรือกันเคสนาฬิกาเพี้ยนที่ `pastMs` ดันมาอยู่ "อนาคต" ของวันปัจจุบัน) → `unit.today`
   - `dayDiff === 1` → `unit.yesterday` (key มีอยู่แล้ว เพิ่มโดย narrative ตามที่ copy gate ขอไว้ในรอบตรวจเดิม)
   - `dayDiff >= 2` → `unit.onWeekday` (key เดิม "{weekdayName} {clockText}") ด้วยชื่อวันของ `pastMs` เอง — **ครอบทั้ง "ภายใน 7 วัน" และไกลกว่านั้นด้วยสูตรเดียวกัน** (ตัดสินใจง่ายกว่า 4 bucket): ยอมรับความคลุมเครือของชื่อวันที่ไม่บอกว่า "สัปดาห์ไหน" เมื่อเกิน 7 วัน เพราะ (ก) บรรทัดนี้แสดง run **ล่าสุดเพียงรายการเดียว** ไม่ใช่ประวัติหลายรายการที่ความเข้าใจผิดเรื่องวันจะสะสม (ข) ไม่มี copy key รูปแบบวันที่ปฏิทินเต็ม (เช่น "DD/MM") ในเฟสนี้ และการเพิ่ม key ใหม่เกินขอบเขตของ "should" นี้ (ค) ข้อความไม่ได้กล่าวอ้างว่า "ล่าสุด"/"สัปดาห์นี้" ที่จะทำให้เข้าใจผิดเป็นเท็จ เป็นแค่ชื่อวันจริงของวันนั้น — **ถ้าในอนาคตมีจอประวัติ run หลายรายการ (list) ให้กลับมาทบทวนจุดนี้ใหม่ เพราะตอนนั้นความคลุมเครือข้ามสัปดาห์จะสะสมจริง**
3. **ชื่อ dungeon (ปิด "hide the dungeon name when unresolved"):** ใช้ `isResolvedDungeonName(nameKey, shortName)` ตัวเดิม (แพทเทิร์นเดียวกับที่ `nav-panel.ts`/`dungeons/artifact.ts` ใช้อยู่แล้ว) — `false` แล้วตัดทั้งท่อนชื่อ (และตัวคั่นข้างมันหนึ่งตัว) ออกทั้งหมด ไม่ใช่ปล่อยชื่อดิบหรือช่องว่างค้าง
4. **ประกอบสตริง:** resolve แล้ว → `"{หัวข้อ} · {ชื่อสั้น} · {เวลา}"` · ไม่ resolve → `"{หัวข้อ} · {เวลา}"` (ตัวคั่น " · " ตามที่ copy gate เสนอไว้ในตารางข้อค้นพบเดิม) — ไม่มี summary เลย (`lastSummary === null`) ยังใช้ `home.recentRunsEmpty` เดิมไม่เปลี่ยน
5. **ไม่มี copy key ใหม่จากงานนี้**: `unit.yesterday`/`unit.onWeekday`/`run.summary.*` ทุกตัวมีอยู่แล้วใน `copy.th.json`
