## 1. ขอบเขตของแผนนี้

แผนนี้ตอบ 3 อย่างที่ P2-F06-T27/T28 ต้องใช้:

1. **แหล่งข้อมูล** ที่จะรวบรวมและวิธีเชื่อมโยงกัน (แบบสอบถาม, telemetry export, บันทึกผู้สังเกต)
2. **วิธีคำนวณ north star proxy ฝั่ง client** ของ Phase 2 ทีละขั้นตอน (PM-S3) — เพราะยังไม่มี server และไม่มี dashboard อัตโนมัติ (D-088)
3. **เกณฑ์ตัดสิน "ไปต่อ / แก้ก่อน / ยกระดับให้ HUMAN"** ที่ตั้งไว้ล่วงหน้า ก่อนเห็นผลจริงจาก playtest — P2-F06-T28 ใช้เกณฑ์นี้เขียนรายงาน ไม่มีสิทธิ์ปรับตัวเลขเกณฑ์หลังเห็นผล (มีแค่สิทธิ์ตีความว่าเข้าเกณฑ์ไหนตามที่นิยามไว้)

**นอกขอบเขต:** การตัดสิน Go/No-go ของการเปิดตัวจริง (เป็นของ F01/GR-1, ปิดแล้ว), การเปลี่ยนสูตร damage/auto-retreat/gate (เป็นของ game-director/systems-designer เท่านั้นตาม CLAUDE.md ข้อ 6), การอนุมัติเปลี่ยน build ระหว่างเดิน (ห้ามเด็ดขาดตาม P-3/F-20 ด้านล่าง)

## 2. ข้อจำกัดที่กำหนดรูปแบบของแผนนี้ (ต้องอ่านก่อนตีความผลทุกครั้ง)

- **N ต่ำ (อย่างน้อย 3 คน, P2-F06-T27):** ทุกตัวเลขในเอกสารนี้เป็น **สัญญาณทิศทาง ไม่ใช่สถิติมีนัยสำคัญ** (PRD F04 §4 ย้ำไว้แล้ว) — ห้ามสรุปเป็นเปอร์เซ็นต์ประชากรจริง
- **P-3/F-20 (ล็อกแล้วใน flow-approval):** playtest ต้อง**ไม่แก้ gate, auto-retreat, damage หรือ config ใดของ build ที่ผู้ร่วมเล่น** — ปรับได้แค่ kit/แบบสอบถาม/การตรวจภาคสนาม ดังนั้นแผนนี้จึง **ไม่ตั้งเกณฑ์ผ่าน/ไม่ผ่านของ HP/auto-retreat จากประสบการณ์ผู้เล่นโดยตรง** (ดูหัวข้อ 6.3)
- **R-P2-06:** เลเวล 1 แทบไม่มีใครเห็น auto-retreat ใน playtest 30–60 นาที (ไม่มียา ~40–70 นาทีถึง auto-retreat, มียาจากดร็อป ~51–116 นาที ตาม balance-model §17.8/§18.3) และเลเวลอัปแรกเกิดที่ tick 4 (~20 นาที) — สัญญาณ HP/auto-retreat ที่แท้จริงมาจาก **การเดินตรวจของทีม (qa F06-C32)** บนเครื่องจริงที่ dungeon ซึ่ง `level_range.min > 1` ไม่ใช่จากผู้ร่วม playtest ทั่วไป
- **ไม่มี dashboard อัตโนมัติ (D-088, metrics.md §1.1):** ทุกไฟล์ export ต้องรวบรวมด้วยมือ คำนวณ proxy ต่อไฟล์ก่อนค่อยเฉลี่ยรวม
- **Confound หน้าจอล็อก (metrics.md §10.1):** north star proxy ของ Phase 2 มีแนวโน้ม**ต่ำกว่าจริง**สำหรับผู้เล่นที่เก็บมือถือในกระเป๋าจริงตามที่เกมสื่อสาร (ก่อนมี Wake Lock ทำงานเต็มรูป) — ต้องอ่านคู่กับ `wake_lock_engaged_share_bucket`/`page_hidden_total_s_bucket` ของแต่ละ run เสมอ ห้ามอ่านตัวเลขเดี่ยวๆ
- **A-P2-H45-1 (รับทราบแล้ว, P2-H50 — นับขาดเมื่อ reload กลาง run):** tech gate F06 รอบ 1 (F06-TG-13) ยืนยันว่า `kw.p2.runClientStats` ที่ใช้คำนวณ `dungeon_exited.page_hidden_total_s_bucket` และ `wake_lock_engaged_share_bucket` อยู่ใน**หน่วยความจำของ `WakeLockController` เท่านั้น** ไม่ persist ลง storage — ถ้าเบราว์เซอร์ reload หน้าเว็บระหว่าง run (kill tab เพราะหน่วยความจำเต็ม, ผู้เล่นกด refresh เอง) ตัวนับเริ่มใหม่จากศูนย์จนถึง `dungeon_exited` ครั้งถัดไป ทำให้**สอง bucket นี้ต่ำกว่าค่าจริงเสมอเฉพาะ run ที่มี reload เกิดขึ้นจริง** (ไม่ใช่ทุก run) ยอมรับเป็นข้อจำกัดของ Phase 2 ไม่ใช่บั๊กที่ต้องแก้ก่อน playtest รอบนี้ — **ผลต่อแผนวิเคราะห์นี้:** อ่านสอง bucket นี้เป็น**ค่าต่ำสุดที่เป็นไปได้ (lower bound) ไม่ใช่ค่าจริง** เมื่อทำหัวข้อ 4.1 ข้อ 7 ถ้าสงสัยว่า run ใดมี reload เกิดขึ้น (สังเกตจาก `session_state_discarded`/`storage_quota_exceeded` ก่อนหน้าใน export เดียวกัน หรือฟอร์มผู้สังเกตบันทึกว่าหน้าจอรีโหลด/ค้าง) ให้ตัดคู่ `page_hidden_total_s_bucket`/`wake_lock_engaged_share_bucket` ของ run นั้นออกจากตารางสรุปเชิงปริมาณและบันทึกเป็นข้อสังเกตแยกแทน — **ไม่กระทบ north star proxy** (หัวข้อ 4) เพราะคำนวณจาก `run_tick_granted` คนละแหล่งข้อมูลกับ `runClientStats`

## 4. วิธีคำนวณ North Star Proxy ฝั่ง Client (PM-S3, PRD F05 §4, metrics.md §1.1)

**นิยามที่ต้องรักษาไว้ทุกตัวอักษร (ห้ามคิดสูตรใหม่ตอนคำนวณจริง):** ผลรวมนาทีที่ run อยู่ Active และมีอย่างน้อย 1 `run_tick_granted` ในหน้าต่าง `config: dungeons.movementGate.window_s` (= 300 วินาที = 5 นาที) เดียวกัน ต่อผู้เล่นต่อ session — คำนวณจาก event เดียวกับที่ตัดสินรางวัลจริง ไม่ใช่เวลาที่แอปเปิดค้าง

### 4.1 ขั้นตอนต่อไฟล์ export 1 ไฟล์ (1 คน)

1. เปิดไฟล์ export (JSONL) เทียบ envelope กลางของ `product/telemetry-events.md` §1
2. แยกกลุ่ม event เป็นราย run โดยใช้คู่ `dungeon_entered` → `dungeon_exited` ถัดไปของ `dungeon_id` เดียวกัน (Phase 2 เล่นได้ทีละ 1 run เท่านั้น ตาม F04-R01 จึงไม่มีปัญหา interleave)
3. ต่อ run หนึ่ง: นับจำนวน `run_tick_granted` ทั้งหมดที่เกิดระหว่าง `dungeon_entered` ถึง `dungeon_exited` ของ run นั้น (**นับรวม event ที่ `partial = true` ด้วย** เพราะยังนับเป็น "มี run_tick_granted อย่างน้อย 1 ครั้งในหน้าต่างนั้น" ตามนิยาม แม้จะเป็น tick บางส่วน)
4. `proxy_minutes(run) = จำนวน run_tick_granted ของ run นั้น × (300/60)` = จำนวน tick × 5 นาที
5. **ข้อประมาณที่ยอมรับได้ (บันทึกไว้เสมอ ไม่ปรับแก้):** ถ้า tick สุดท้ายของ run เป็น partial (`dungeon_exited.partial_tick_applied = true`) วิธีนี้นับหน้าต่างนั้นเป็น 5 นาทีเต็มทั้งที่เวลาที่ผ่านจริงของหน้าต่างนั้นอาจสั้นกว่า — เป็นการประมาณสูงกว่าจริงเล็กน้อยเฉพาะ tick สุดท้ายต่อ run (สอดคล้องกับ PRD F05 §4 assumption A-P2-F05-T02-1 ที่ระบุว่าไม่ปรับ scale ใดๆ ใน Phase 2)
6. `proxy_minutes(player) = ผลรวม proxy_minutes(run) ของทุก run ที่คนนั้นเล่นระหว่าง session ภาคสนาม`
7. บันทึกคู่กับ `wake_lock_engaged_share_bucket` และ `page_hidden_total_s_bucket` ของแต่ละ run (จาก `dungeon_exited`) เพื่อกางหมายเหตุ confound หัวข้อ 2 เสมอ — **อ่านสอง bucket นี้เป็น lower bound ตาม A-P2-H45-1 (หัวข้อ 2)** ถ้า run นั้นมีสัญญาณว่า reload เกิดขึ้นกลางทาง

### 4.2 รวมผลข้ามคน (manual aggregation, D-088)

- เอา `proxy_minutes(player)` ของทุกคน (P1..Pn) มาใส่ตารางเดียว พร้อม `duration_s_bucket` ของ run และ `class`
- รายงาน **ค่าเฉลี่ย, ค่ากลาง (median), ต่ำสุด-สูงสุด, N** — ไม่รายงานค่าเฉลี่ยเดี่ยวๆ เพราะ N ต่ำมาก (ตามหัวข้อ 2)
- แบ่งกลุ่มตาม class เสมอ (metrics.md §3.1 บังคับ) — ห้ามรวมทุก class เป็นตัวเลขเดียวก่อนรายงานแยก
- เทียบสัดส่วน `proxy_minutes(player) / เวลาที่เล่นจริงทั้งหมด (นาที ตามข้อ 1 ของแบบสอบถาม)` เป็น "สัดส่วนเวลาที่เดินแล้วนับได้จริง" — ใช้คู่กับข้อ 4.2/4.3 ของแบบสอบถาม (ความรู้สึกว่าได้ tick สม่ำเสมอ) เพื่อดูว่าตัวเลขกับความรู้สึกตรงกันไหม

## 6. เกณฑ์ตัดสิน "ไปต่อ / แก้ก่อน / ยกระดับให้ HUMAN" (ล็อกก่อนเห็นผล)

หลักการอ่านหัวข้อนี้: แบ่งเป็น **3 ระดับความรุนแรง** ต่อ "สิ่งที่พบ" ไม่ใช่ต่อ "ฟีเจอร์" — playtest หนึ่งครั้งอาจได้ทั้ง PASS บางเรื่องและ FIX-FIRST บางเรื่องพร้อมกัน รายงาน P2-F06-T28 ต้องเรียงรายการตามผลกระทบ (acceptance ของ T28) ไม่ใช่สรุปเป็นคำเดียวทั้งฉบับ

### 6.1 ระดับ "ไปต่อได้" (PASS) — เข้าเกณฑ์นี้เมื่อครบทุกข้อ

1. ผู้เข้าร่วมอย่างน้อย 2 ใน 3 คน (หรือเสียงข้างมากถ้า N มากกว่า) ตอบข้อ 3.1 ("เข้าใจต้องเดินไปหา dungeon โดยไม่ต้องอธิบายเพิ่ม") ที่ 4 หรือ 5
2. ไม่มีบั๊กที่ทำให้ **ไม่มีใครถึงรางวัลก้อนแรก** ภายในเวลาที่เดินจริงของรอบนั้น (ยกเว้นกรณีระยะทางเดินจริงเกินคาดจาก location-engineer ระบุแยกไว้แล้วว่าเป็นกรณีศึกษา ตาม A-P2-F04-T02-2)
3. เฉลี่ยข้อ 9.1 ("พรุ่งนี้น่าจะเปิดเกมเดินอีก") ≥ 3.5 จาก 5 (คำนวณจากทุกคนที่ตอบ ไม่ตัดใครออก)
4. ไม่มีเหตุการณ์ความปลอดภัยจริงระหว่างเดิน (ตาม safety briefing — ถ้ามี ระดับนี้ตกทันทีไม่ว่าตัวเลขอื่นจะดีแค่ไหน)
5. ไม่มีข้อค้นพบใดเข้าเกณฑ์ระดับ 6.2 ด้านล่าง

### 6.2 ระดับ "แก้ก่อนไปต่อ" (FIX-FIRST) — เข้าเกณฑ์นี้เมื่อพบข้อใดข้อหนึ่ง

1. เสียงข้างมากของผู้ร่วม (≥ 2 ใน 3 หรือเทียบสัดส่วน) ตอบข้อ 3.3 หรือ 4.2 หรือ 4.3 ต่ำกว่า 3 — แปลว่าความเข้าใจ core loop หรือความรู้สึกต่อ movement gate มีปัญหาเป็นวงกว้าง ไม่ใช่แค่คนเดียว
2. เจอ `no_approach_from_outside` (ข้อ 5.2) ที่ "มากกว่า 3 ครั้ง" จากผู้ร่วมคนใดคนหนึ่ง **และ** ข้อ 5.2b ตอบ "ไม่เข้าใจ/รู้สึกว่าเกมงอแง"
3. ข้อ 5.4 ("จุดที่ดูใกล้แต่เดินเข้าไม่ถึงจริง") มีผู้ร่วมเจออย่างน้อย 1 คน **และ** เป็น dungeon เดียวกับที่นัดใน kit (ไม่ใช่ทางเบี่ยงชั่วคราวนอกแผน) — ปัญหานี้กระทบความปลอดภัยทางกายภาพโดยตรงตาม GDD จึงไม่รอสะสมหลายคนก่อนแก้
4. เฉลี่ยข้อ 8.1 ("อยากลองใหม่ไหมหลังเจอหน้าจอไกล/นอกพื้นที่") อยู่ที่ "ไม่อยากแล้ว" จากผู้ร่วมที่เจอหน้าจอนี้ตั้งแต่ 1 คนขึ้นไป — ผูกกับ GR-2 ของ metrics.md โดยตรง
5. มีบั๊กที่ qa-tester บันทึกใน `qa/bugs.md` ระดับ high หรือ critical ที่เกิดระหว่าง playtest (cross-check กับ P2-F06-T21 QA gate)
6. เฉลี่ยข้อ 9.2 ("การเดินคุ้มกับสิ่งที่ได้รับ") ต่ำกว่า 3 จากผู้ร่วมส่วนใหญ่ — สัญญาณว่า reward feedback (F05 §6.3) ไม่จูงใจพอ
7. **(ใหม่ — P2-H24, GD Q-8)** เสียงข้างมากของผู้ร่วมที่เห็นข้อความ `run.tickDenied` (ตอบข้อ 4.1b ของแบบสอบถามว่าเจอ ไม่ใช่ "ไม่เจอข้อความนี้เลย") เลือกตัวเลือก (ค) "เกมค้างหรือมีบั๊ก" หรือ (ง) "เกมลงโทษฉัน" — สัญญาณว่า copy/UX ของข้อความนี้สื่อสารไม่ได้ผล **แก้ที่ copy/UX เท่านั้น (ส่ง narrative-designer + uiux-designer) ไม่ใช่การแก้ค่า movement gate** — ข้อเสนอแก้ค่า gate จากข้อค้นพบนี้ต้องผ่านหัวข้อ 6.4 (game-director + HUMAN ทุกขนาด, D-128) ไม่ใช่แก้ตรงนี้เงียบๆ

### 6.3 สิ่งที่ **ไม่ใช่** เกณฑ์ตัดสิน go/no-go ของ F06 รอบนี้ (ต้องระบุชัดในรายงานทุกครั้ง)

- **HP ต่ำ/auto-retreat/การตาย จากประสบการณ์ผู้เล่นใน playtest ไม่ใช้เป็นเกณฑ์ PASS/FIX-FIRST** เพราะ R-P2-06 ยืนยันแล้วว่าเลเวล 1 ส่วนใหญ่ไม่เห็นเหตุการณ์นี้เลยในเวลา 30–60 นาที (ไม่ใช่ปัญหาของฟีเจอร์ที่ต้องแก้ เป็นผลตั้งใจของ D-112) — สัญญาณจริงของ HP/auto-retreat มาจากการเดินตรวจของทีม (F06-C32) และ P2-F06-T17 (black-box) เท่านั้น ถ้าแบบสอบถามข้อ 7.x มีคนตอบได้ (เจอเหตุการณ์จริง) ให้รายงานเป็น **ข้อมูลเสริมเชิงคุณภาพ** ไม่ใช่เกณฑ์ปิดเกต
- **การปรับ gate/auto-retreat/damage/config เพื่อ "ให้เห็นผลชัดขึ้น" ระหว่าง playtest เป็นสิ่งต้องห้าม** ตาม P-3/F-20 — ถ้าพบว่าอยากเห็นสัญญาณนี้เพิ่ม ให้เสนอเป็น handoff ไปที่ qa-tester/level-designer ให้เลือก dungeon ที่ `level_range.min > 1` สำหรับรอบเดินตรวจของทีมแทน ไม่ใช่แก้ build ของผู้ร่วม playtest
- N ต่ำมาก (≥3 คน) จึงไม่มีเกณฑ์ใดที่อ้างอิงเปอร์เซ็นต์ที่ต่ำกว่า "เสียงข้างมากอย่างชัดเจน" (≥2 ใน 3) ได้อย่างมีความหมายทางสถิติ — ทุกเกณฑ์ข้างต้นใช้หน่วยนับคน ไม่ใช่เปอร์เซ็นต์ทศนิยม

### 6.4 ระดับ "ยกระดับให้ HUMAN ตัดสิน" (ไม่ใช่อำนาจ product-manager คนเดียว)

- พบเหตุการณ์ความปลอดภัยจริงระหว่างเดิน (บาดเจ็บ, เกือบเกิดอุบัติเหตุ, ผู้ร่วม 15–17 ปีอยู่โดยไม่มีผู้ใหญ่/ทีมตามที่ D-092 กำหนด)
- **(แก้ตาม D-128, P2-H24, GD Q-9 — เลิกใช้กฎ ±20%)** ข้อค้นพบใดชี้ว่าอาจต้องเปลี่ยนค่า **movement gate** (`config: dungeons.movementGate.*`) หรือ **ค่าเริ่มต้นของ auto-retreat** จากผล playtest — **การเปลี่ยนค่าสองกลุ่มนี้ทุกขนาด (ไม่ว่าเล็กแค่ไหน) ต้องผ่าน game-director และ HUMAN เสมอ ไม่ใช้กฎ "เกิน ±20% ของ GDD จึงส่งคน"** เพราะทั้งสองเป็นค่าที่ GDD กำหนดตรงและเป็น non-negotiable (NN-2, NN-6) ไม่ใช่ค่าปรับสมดุลทั่วไปที่ systems-designer ปรับเองได้ภายใน ±20% ตามโครง decision authority ปกติของ protocol ข้อ 5 — ส่งเป็น handoff ก่อน P2-F06-T29 เสมอไม่ว่าขนาดที่เสนอแก้จะเท่าไร (ค่า config อื่นที่ไม่ใช่สองกลุ่มนี้ เช่น balance ทั่วไปของไอเทม/ดรอป ยังใช้กฎ ±20% ของ protocol ข้อ 5 ตามเดิม ไม่เปลี่ยน)
- ผู้ร่วม playtest ไม่ครบ 3 คน หรือกลุ่ม 15–17 ปีไม่มีฟอร์มผู้ปกครองครบ (R-P2-16) — ไม่มีเกณฑ์ในเอกสารนี้ตัดสินแทน ต้องรายงานเป็นข้อจำกัดของข้อมูลตรงๆ ให้ HUMAN ตัดสินว่าจะยอมรับ N ที่ได้จริงหรือนัดเพิ่ม

## 7. การแบ่งกลุ่มผลที่บังคับทำเสมอ (segmentation)
