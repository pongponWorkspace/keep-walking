## 1. กรอบที่ใช้ตรวจ

เกณฑ์ spike M1 ไม่ใช่แค่ "แผนที่ลื่นหรือไม่" ในทางวิศวกรรม แต่ต้องตอบว่า **คนสามกลุ่มเป้าหมายเล่นเกมนี้ได้จริงไหมในสภาพจริง**:

1. ผู้เล่นเวลาน้อย (~40 นาที/วัน) — ต้องเห็นแผนที่และรอยแยกเร็ว, GPS fix เร็ว, check-in ผ่านตั้งแต่ครั้งแรก เพราะไม่มีเวลาเผื่อสำหรับความล้มเหลว
2. ผู้เล่นเวลามาก (3–6 ชม./วัน) — ต้องอยู่ได้ทั้ง session โดยแบตไม่หมดกลางทาง และ data ไม่กินแพ็กเกจเดือนจนต้องเลิกเล่น
3. คนอยู่นอกพื้นที่เล่น / คนอยู่บ้านตอนฝนตก — อยู่นอกขอบเขตของ spike นี้โดยตรง (F01/F06 รับผิดชอบ) แต่ accuracy ในซอย (S10) และการอ่านจอกลางแดด (S17) เกี่ยวกับ "คนที่พื้นที่เล่นเป็นย่านเมืองแออัด ไม่ใช่สวนโล่ง" ซึ่งเป็นเงื่อนไขจริงของกรุงเทพฯ

ยึดหลักการที่ใช้ตัดสินทุกข้อขัดแย้งของ GDD ข้อ 2 และ 3 เป็นแกน: **รางวัลผูกกับการเคลื่อนไหวจริงเสมอ** และ **ต้นทุนเดินทางสูง บทลงโทษต้องต่ำ** — เกณฑ์ใดที่กระทบว่าคนที่เดินจริงจะได้รางวัลจริงหรือไม่ (S9, S11, S12) ต้องเป็นเกณฑ์เด็ดขาดที่สุด เกณฑ์ที่กระทบแค่ความสวยงามหรือความเร็วเสริม (S16, S17) เป็นเกณฑ์มีทางเลือกได้

## 2. ผลตรวจ S1–S17 และ I1–I2

รูปแบบ: ค่าตามตาราง 10.1 ของ tech note (ไม่เปลี่ยน) · ความเห็น PM (ยืนยัน / เสนอค่าใหม่) · เหตุผลเชิงผู้เล่น · ประเภทเด็ดขาด (Hard = No-go ถ้าพลาด) หรือมีทางเลือก (Soft = Go พร้อมเงื่อนไข)

### S1 — FPS ระหว่าง pan/zoom
- ค่า: Go ≥50 & p5≥30 / เงื่อนไข เฉลี่ย 30–<50 หรือ p5 20–<30 / No-go เฉลี่ย <30 หรือ p5 <20
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: ผู้เล่นดูแผนที่ตอนเปิดแอปครั้งแรก (นาที 0–1) และตอนหาเส้นทางไป dungeon ถ้าลากแผนที่แล้วกระตุก คนกลุ่ม 40 นาที/วันจะรู้สึกว่าแอปพัง ก่อนถึงขั้นได้เห็นรอยแยกด้วยซ้ำ
- ประเภท: เด็ดขาด (Hard) — ยืนยัน

### S2 — FPS โหมดตามตัว
- ค่า: เหมือน S1
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: นี่คือโหมดที่ใช้งานจริงระหว่างเดินเข้า dungeon และตอนอยู่ใน run — ตรงกับคำถามหลักของ M1 ("จุดตำแหน่งขยับตามจริงไหม") มากกว่า S1 เสียอีก
- ประเภท: เด็ดขาด (Hard) — ยืนยัน

### S3 — แบตต่อ 30 นาที (จอเปิดตลอด)
- ค่า: Go ≤10% / เงื่อนไข >10–15% / No-go >15%
- PM: **ยืนยัน** ตัวเลข พร้อมข้อสังเกตเพิ่มในหัวข้อ 4 (ไม่ใช่การเสนอเปลี่ยนค่า)
- เหตุผลเชิงผู้เล่น: กลุ่มเวลาน้อยเล่น ~40 นาที ใช้แบตราว 13–20% ยังเหลือทั้งวัน กลุ่มเวลามาก 2 ชม. ใช้ 40–60% ยังพอกลับบ้านได้ถ้าเริ่มจากแบตเต็ม เกิน 15% ต่อ 30 นาทีคือคนจะเลิกเล่นกลางทางเพราะกลัวแบตหมดระหว่างเดินทางกลับ ซึ่งขัดหลัก "ต้นทุนเดินทางสูง บทลงโทษต้องต่ำ" โดยตรง (แบตหมดกลางทางคือบทลงโทษที่หนักที่สุด)
- ประเภท: เด็ดขาด (Hard) — ยืนยัน

### S4 — เวลาจนแผนที่แรกขึ้น
- ค่า: Go ≤3s / เงื่อนไข 3–6s / No-go >6s
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: งบเวลาทั้งนาที 0–1 ของ onboarding ต้องรวม consent + permission + age gate + login + เลือกพลัง + เห็นแผนที่ (`design/ux/flows/F03-core-loop.md` หัวข้อ 2) ซึ่งแน่นอยู่แล้ว (ดู [ASSUMPTION A-P1-F03-T16-1]) แผนที่เองกิน 6 วินาทีเต็มจะดันภาพรวมเกินนาทีแรกจริง จึงต้องเข้มที่ 6s = No-go เด็ดขาดเชิงเวลา แต่ผลกระทบไม่ใช่การเล่นไม่ได้ทั้งหมด (แค่ onboarding ช้า) จึงยังเป็น Soft ตามที่ tech note จัด
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S5 — MB ของ JS (cache ว่าง)
- ค่า: Go ≤1.0MB / เงื่อนไข 1.0–2.0MB / No-go >2.0MB
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: กระทบผู้เล่นทางอ้อมผ่าน S4 (เวลาโหลดแรก) และ S8 (data รวม) ไม่มีผลตรงต่อประสบการณ์นอกจากนั้น เหมาะเป็นงบวิศวกรรมมีทางเลือก
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S6 — MB ของ style + glyph + sprite + font (cache ว่าง)
- ค่า: Go ≤1.0MB / เงื่อนไข 1.0–3.0MB / No-go >3.0MB
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: เช่นเดียวกับ S5 กระทบทางอ้อมผ่าน S4/S8 · font ไทยที่โหลดหนักเกินจะทำให้คนใหม่เห็นแผนที่ช้าในนาทีแรกด้วย แต่ตัวเลขเองไม่ใช่จุดที่ผู้เล่นสัมผัสตรง
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S7 — MB ของ tile ใน 30 นาทีที่เดิน
- ค่า: Go ≤10MB / เงื่อนไข 10–25MB / No-go >25MB
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: ผู้เล่นเดินไปเรื่อยๆ ทำให้แผนที่โหลด tile ใหม่ตลอด ยิ่งเดินไกล (กลุ่มเวลามาก) ยิ่งโหลดเยอะ ตัวเลขนี้เป็นองค์ประกอบของ S8 ซึ่งเป็นตัวที่กระทบผู้เล่นจริง
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S8 — MB รวมใน 30 นาที (S5+S6+S7)
- ค่า: Go ≤12MB / เงื่อนไข 12–30MB / No-go >30MB
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: นี่คือตัวเลขที่ผู้เล่นสัมผัสจริงผ่านค่าเน็ตมือถือ (ไม่ใช้ Wi-Fi กลางแจ้ง) 12MB/30นาที ≈ 72MB/3ชม./วัน ยังอยู่ในแพ็กเกจทั่วไป ส่วน >30MB/30นาที ≈ 5GB/เดือนถ้าเล่นทุกวันเกินแพ็กเกจราคาถูกที่กลุ่มเวลาน้อย (รายได้จำกัดกว่า) มักใช้ — ตรงกับ north star "walking minutes ต่อสัปดาห์" เพราะ data ที่แพงเกินจะทำให้คนไม่กลับมาเล่นซ้ำ ถูกต้องแล้วที่เป็นตัวรวมผลเด็ดขาดแม้ตัวย่อยแต่ละตัวเป็น Soft — นี่คือรูปแบบ aggregation ที่ดี (องค์ประกอบยืดหยุ่นได้ แต่ผลรวมที่ผู้เล่นจ่ายจริงต้องไม่เกิน)
- ประเภท: เด็ดขาด (Hard) — ยืนยัน

### S9 — accuracy ในสวน (median/p90)
- ค่า: Go ≤10m & ≤20m / เงื่อนไข median≤15m & p90≤30m / No-go median>15m หรือ p90>30m
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: ผูกตรงกับ `checkIn.maxAccuracy_m` = 30m — ถ้า p90 เกิน 30m แปลว่าผู้เล่น 1 ใน 10 คนยืนอยู่หน้า dungeon จริงแต่ระบบไม่ยอมให้เข้า (GPS บอกว่ายังไม่ถึง) นี่คือความรู้สึกแย่ที่สุดที่ GDD ต้องการหลีกเลี่ยง (เดินมาจริงแต่เกมไม่ยอมรับ) ตรงกับหลักการข้อ 3 ของ GDD โดยตรง
- ประเภท: เด็ดขาด (Hard) — ยืนยัน

### S10 — accuracy ในซอย (median/p90)
- ค่า: Go ≤20m & ≤35m / เงื่อนไข median≤30m & p90≤50m / No-go median>30m หรือ p90>50m
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: ตึกสูงบังสัญญาณในซอยเป็นข้อจำกัดทางกายภาพที่แก้ด้วยซอฟต์แวร์ไม่ได้เต็มที่ (GDD "ข้อจำกัดที่กำหนดรูปร่างของ design" — GPS ในอาคารไม่แม่น) dungeon ส่วนใหญ่ตาม preset (สวนใหญ่/ตลาด/สวนหย่อม) ควรอยู่ในที่โล่งกว่าซอยแคบอยู่แล้ว ค่านี้จึงเป็นข้อมูลเผื่อกรณี dungeon แบบตลาดที่อยู่ในซอย ไม่ใช่กรณีทั่วไปของทุก dungeon สมควรเป็นเงื่อนไขไม่ใช่ตัวตัดสิทธิ์ทั้งหมด
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S11 — เวลาจน fix แรกที่ accuracy ≤30m ในสวน (TTFF)
- ค่า: Go ≤15s / เงื่อนไข 15–45s / No-go >45s
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: ผู้เล่นเดินถึงขอบ dungeon แล้วต้องรอ GPS ล็อกก่อนกดเข้า (popup confirm ต้องมีตำแหน่งที่แม่นพอ) รอเกิน 45 วินาทีหลังเดินมาถึงจริงคือความหงุดหงิดที่ทำลายความรู้สึก "มาถึงแล้ว" พอดี — ยังจัดเป็น Soft เพราะมีทางแก้ระยะสั้น (รอเพิ่ม, ขยับที่โล่ง) ไม่ใช่ทางตัน
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S12 — % หน้าต่าง 5 นาทีที่ผ่าน movement gate ขณะเดินต่อเนื่องในสวน
- ค่า: Go ≥95% / เงื่อนไข 85–<95% / No-go <85%
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: นี่คือหลักการข้อ 2 ของ GDD ("รางวัลผูกกับการเคลื่อนไหวจริงเสมอ ไม่มีข้อยกเว้น") ตัวเลขนี้วัดด้านกลับ: คนที่เดินจริงต้องได้รางวัลจริงเกือบทุกครั้ง ถ้าตกเกิน 15% ของเวลาทั้งที่เดินต่อเนื่องจริง แปลว่า GPS/เทคนิคทำให้เกมไม่แฟร์กับคนที่ทำสิ่งที่เกมอยากให้ทำพอดี ซึ่งเป็นความเสี่ยงต่อการ "come back" โดยตรง (คนจะรู้สึกโดนโกงและเลิกเล่น)
- ประเภท: เด็ดขาด (Hard) — ยืนยัน

### S13 — sample ขาด >10 วินาที (% ของเวลา)
- ค่า: Go ≤2% / เงื่อนไข 2–5% / No-go >5%
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: เป็นสาเหตุหนึ่งที่ทำให้ S12 ตก แต่ S12 เป็นตัวเลขที่ผู้เล่นสัมผัสจริง (ได้/ไม่ได้รางวัล) ส่วน S13 เป็นตัวชี้เหตุเชิงเทคนิค จึงเหมาะเป็น Soft ไม่ต้อง duplicate ความเข้มกับ S12
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S14 — ช่วงห่างระหว่าง fix (median)
- ค่า: Go ≤2s / เงื่อนไข 2–5s / No-go >5s
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: กระทบความลื่นของจุดตำแหน่ง (S15) และความแม่นของ S12 ทางอ้อม ไม่ใช่ตัวเลขที่ผู้เล่นเห็นตรงๆ
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S15 — ความหน่วงของจุดตำแหน่ง (median/p90)
- ค่า: Go ≤1.5s & ≤3s / เงื่อนไข median≤3s & p90≤5s / No-go เกินกว่านั้น
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: ที่ความเร็วเดินเท้าปกติ (~1.4 m/s) หน่วง 3–5 วินาที = จุดคลาดจากตำแหน่งจริงราว 4–7 เมตร ยังพอรับได้สำหรับเกมที่ไม่ใช่ real-time twitch (เกมนี้เป็นเกม "เดินแล้วรอ tick" ไม่ใช่เกมที่ต้องตอบสนองทันที) จึงเหมาะเป็น Soft แม้จะตรงกับคำถามหลักของ M1 ("จุดตำแหน่งขยับตามจริงไหม") ก็ตาม เพราะผลของการพลาดคือ "รู้สึกหน่วงเล็กน้อย" ไม่ใช่ "เล่นไม่ได้"
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S16 — ป้ายภาษาไทยผิดตำแหน่ง/ทับกัน/เป็นกล่อง (20 ป้าย, 3 zoom)
- ค่า: Go 0 ป้าย / เงื่อนไข 1–2 ป้ายแต่ยังอ่านออก / No-go ≥3 ป้าย หรือมีป้ายอ่านไม่ออก
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: ชื่อสถานที่ภาษาไทยที่อ่านไม่ออกกระทบการหาทางแต่ไม่ใช่ทางตัน (มีชื่อ dungeon และ HTML marker ตาม fallback F3 ในหัวข้อ 12 ของ tech note ที่ใช้ text engine เต็มรูปอยู่แล้ว) จึงเหมาะเป็น Soft
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

### S17 — อ่านแผนที่และจุดตำแหน่งกลางแดด
- ค่า: Go อ่านได้ทันที / เงื่อนไข อ่านได้เมื่อบังแดด/เร่งความสว่าง / No-go อ่านไม่ได้แม้บังแดด
- PM: **ยืนยัน**
- เหตุผลเชิงผู้เล่น: กรุงเทพฯ แดดจัดเกือบทั้งปี (GDD "กรุงเทพร้อนและฝนตก 6 เดือน") ผู้เล่นกลุ่มเวลาน้อยมักเล่นตอนพักกลางวันหรือระหว่างเดินทาง ซึ่งเป็นช่วงแดดแรง การบังแดดด้วยมือ/ร่มเป็นพฤติกรรมที่คนไทยทำอยู่แล้วเวลาดูมือถือกลางแจ้ง จึงยอมรับเป็นเงื่อนไขได้ ไม่ใช่ทางตัน
- ประเภท: มีทางเลือก (Soft) — ยืนยัน

- ประเภท: ข้อมูลประกอบ — ยืนยันตามที่จัดไว้

## 3. กฎรวมผล (หัวข้อ 10.2 ของ tech note)

PM ยืนยันทั้ง 5 ข้อของกฎรวมผลโดยไม่เสนอเปลี่ยน:

1. ตัดสินแยกต่อเครื่องต่อสถานที่ — ถูกต้อง เพราะ S9/S11/S12 (สวน) กับ S10 (ซอย) เป็นบริบทผู้เล่นคนละแบบ (dungeon โล่งเทียบ dungeon ในย่านแออัด)
2. No-go ถ้ามีตัว "เด็ดขาด" ใดเป็น No-go, Go พร้อมเงื่อนไขถ้ามีตัวใดอยู่ช่วงเงื่อนไขหรือตัว "มีทางเลือก" เป็น No-go — สมเหตุสมผล เพราะทางเลือกในหัวข้อ 12 ของ tech note (F1–F14) กลายเป็นเงื่อนไขบังคับ ไม่ใช่การละเลยปัญหา
3. ผลของ spike = ผลที่แย่กว่าระหว่างสองเครื่อง — ตรงกับ D-003 และป้องกันไม่ให้ทีมเลือกเฉพาะเครื่องที่ผลดีมาอ้าง Go
4. ข้อมูลไม่พอ = ยังตัดสินไม่ได้ ต้องเดินซ้ำ ไม่นับเป็น Go — สำคัญมากจากมุมผู้เล่น เพราะการนับ Go ทั้งที่ข้อมูลไม่พอเสี่ยงเปิดตัวเกมที่ยังพิสูจน์ไม่ได้ว่าเล่นได้จริง
5. เส้นแบ่งพอดีถือ Go — ยอมรับได้ ไม่กระทบผู้เล่นในทางปฏิบัติ (ความต่างที่เส้นแบ่งเล็กน้อยกว่าความคลาดเคลื่อนของการวัดเอง)

## 4. ข้อสังเกตที่ไม่ block การยืนยันเกณฑ์ (non-blocking)

### 4.1 ความขัดแย้งที่อาจเกิดระหว่าง "เก็บมือถือใส่กระเป๋าได้" กับ "ต้องเปิดจอเพื่อนับระยะ"

GDD หัวข้อ "สัญญาณขาดและแอปถูกปิด" ระบุชัดว่า "ล็อกหน้าจอ: v1 บนเว็บ หยุดนับ movement" แต่ `design/ux/flows/F03-core-loop.md` หัวข้อ 4 (Flow C, run state) เขียนว่า "มือถือเก็บกระเป๋าได้ทั้งหมดของ flow นี้" ระหว่างรอ reward tick หากจอปิดล็อกอัตโนมัติระหว่างอยู่ในกระเป๋า (ค่า timeout เริ่มต้นของมือถือส่วนใหญ่ 30 วินาที–2 นาที) ผู้เล่นจะไม่ได้ tick ทั้งที่เดินอยู่จริง ขัดกับ S12 และหลักการข้อ 2 ของ GDD โดยตรง

ตัวชี้วัด I2 ที่มีอยู่แล้วถูกจุดแล้ว (ข้อมูลประกอบ ไม่ผูก Go/No-go ของ spike นี้ตามที่ตั้งไว้ ถูกต้อง เพราะ spike ยังไม่ทดสอบ Wake Lock API หรือพฤติกรรม OS จริง) — PM ยืนยันว่าไม่ต้องเพิ่มเป็นเกณฑ์ S ใหม่ในรอบนี้ แต่ต้องมีคนตัดสินใจเรื่อง Wake Lock/ถ้อยคำ UX ก่อน M2 ไม่เช่นนั้นตัวเลข S3 (แบตต่อ 30 นาที "จอเปิดตลอด") จะประเมินสถานการณ์จริงต่ำกว่าที่ผู้เล่นเจอ เพราะผู้เล่นจริงอาจต้องเปิดจอค้างไว้ตลอด (กิน battery เท่า S3 หรือมากกว่า) เพื่อไม่ให้โดนล็อก ซึ่งขัดกับสมมติฐาน "เก็บกระเป๋าได้" ที่ copy จะสื่อกับผู้เล่น

### 4.2 แบตสำหรับกลุ่มผู้เล่นเวลามาก (3–6 ชม./วัน)

เกณฑ์ S3 ตั้งจากฐาน 30 นาที ไม่ได้นอกใจกลุ่มเวลาน้อย แต่เมื่อคูณตรงไปที่ 3–6 ชม. ต่อเนื่อง (60% ถึง 120% ที่ขอบ No-go 15%) ค่าที่ No-go ยอมรับได้ในทางทฤษฎีจะทำให้แบตหมดกลางวันสำหรับกลุ่มนี้ ไม่เสนอเปลี่ยนตัวเลข S3 (30 นาทีเป็นหน่วยวัดที่ถูกต้องแล้วสำหรับ spike ทางเทคนิค เพราะพฤติกรรมจริงไม่ต่อเนื่องเชิงเส้นแบบนั้น — มีช่วงเดินทาง, พัก, ที่บ้านสลับ) แต่ **เสนอให้ liveops-operator/game-director พิจารณาเป็น input ของ metrics guardrail ("แบตที่ใช้ต่อวันของผู้เล่น heavy session") ใน Phase 2** ไม่ใช่ blocking ต่อ T27

### 4.3 สภาพฝน

Spike นี้ไม่ทดสอบสภาพฝน (kit ของ T14 ทดสอบกลางแดดเท่านั้นตามหัวข้อ 10.4) PM เห็นว่าถูกต้องแล้วที่ไม่รวมในเกณฑ์ M1 เพราะฝนไม่กระทบ FPS/accuracy/data โดยตรง (เป็นปัจจัยพฤติกรรม "เล่นหรือไม่เล่น" ไม่ใช่ปัจจัยเทคนิคของแผนที่/GPS) ประเด็น "DAU ตกช่วงฝน" เป็นความเสี่ยงที่ GDD วางไว้แล้วและอยู่ในขอบเขตของ metrics/live ops ไม่ใช่ spike นี้

## 5. Verdict

**PASS** — เกณฑ์ทั้ง S1–S17 (และ I1, I2) ตามตาราง 10.1 ของ `docs/tech/F02-map-location-spike.md` สะท้อนประสบการณ์ผู้เล่นทั้งสามกลุ่มเป้าหมายได้เหมาะสมแล้ว การจัดประเภทเด็ดขาด/มีทางเลือกของ tech-lead ถูกต้องทุกข้อเมื่อตรวจด้วยหลักการ GDD ("รางวัลผูกกับการเคลื่อนไหวจริงเสมอ", "ต้นทุนเดินทางสูง บทลงโทษต้องต่ำ") ไม่มีการเสนอเปลี่ยนค่าตัวเลขใดใน S1–S17 จึงไม่มี handoff แบบ blocking ถึง tech-lead ในหัวข้อค่าเกณฑ์ · มีข้อสังเกตไม่ block 3 ข้อ (หัวข้อ 4) ที่ส่งเป็น handoff/question ไม่บล็อกการเริ่ม build หน้าวัด (P1-F02-T09/T11) หรือ field-walk kit (P1-F02-T14)
