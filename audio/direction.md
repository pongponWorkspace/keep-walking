## 1. หลักการเสียง 5 ข้อ

1. **สั่นมาก่อนเสียงเสมอ** (pillars P4) — ทุก cue ที่ "สำคัญ" (ต้องรู้แม้ไม่ได้ดูจอ) ออกแบบ vibration pattern ก่อน แล้วค่อยแต่งเสียงให้ตรงจังหวะเดียวกัน ไม่ใช่กลับกัน
2. **ไม่มีเพลงประกอบต่อเนื่อง (background music/ambient loop) ใน v1** — มีแค่ cue สั้นแบบ one-shot ที่ผูกกับ event เท่านั้น เหตุผล: (ก) มือถืออยู่ในกระเป๋าตาม pillars P4 ไม่มีใครฟังเพลงประกอบขณะเดินอยู่กลางตลาด (ข) งบแบตและงบข้อมูล (ค) เสียงเพลงจากกระเป๋ากลางที่สาธารณะไม่เหมาะกับโทน "กรุงเทพจริง" — เพลงจริงเกินขอบเขต v1 เป็น handoff ถึง HUMAN (ดูหัวข้อ 11)
3. **สั้น กลางความถี่ ไม่มีหางเสียงยาว** — cue ทุกตัว ≤ 600 ms (ยกเว้น auto-retreat/death ที่ยาวได้ถึง ~900 ms เพราะเกิดไม่บ่อย) ความถี่หลักอยู่ช่วง 800 Hz–3.5 kHz ที่ลำโพงมือถือเล็กยังส่งออกมาได้ยินและไม่จมกับเสียงรถ (low-frequency) หรือเสียงคนคุย (mid-low)
4. **รู้โดยไม่ต้องดูจอและไม่ต้องมีเสียง** — ทุก signal สำคัญ (HP 30%, auto-retreat, ตาย, raid checkpoint, raid เหลือ 30 นาที) มีชั้นสั่นที่แยกแยะได้จากชั้นอื่นด้วยจังหวะเพียงอย่างเดียว เสียงเป็นชั้นเสริม ไม่ใช่ช่องทางเดียว (ดูหัวข้อ 7–8 และตารางใน cue-list)
5. **โทนแห้ง กวน ไม่ปลอบ ไม่ตกใจเกินจริง** ตาม style-guide หัวข้อ 1 — cue ลบ/แจ้งเตือน (tickDenied, autoRetreat, death) ใช้เสียงที่ "บอกข้อเท็จจริง" ไม่ใช่เสียง error แบบเกมทั่วไป (ไม่มีเสียงพังทลาย ไม่มีเสียงร้องเจ็บ) ส่วน cue บวก (tickGranted, drop) สนุกได้แต่ไม่ celebratory เกินเหตุ เพราะเกิดถี่ทุก 5 นาที

## 3. โทนเสียงและแรงบันดาลใจ

แรงบันดาลใจ: เสียงระฆังประตูรถไฟฟ้า BTS/MRT (สองโน้ตขึ้น แจ้งประตูจะปิด), กระดิ่งรถเข็นก๋วยเตี๋ยว/ไอติม, เสียงออดร้านสะดวกซื้อตอนเปิดประตู, เสียงกดเครื่องคิดเลขร้านทอง — ทั้งหมดนี้เป็น **แรงบันดาลใจด้านจังหวะและ texture เท่านั้น** ห้ามลอกทำนอง จังหวะ หรือ pitch ที่ตรงกับของจริงจนจำได้ (เข้าเงื่อนไข P5 "ห้ามแตะแบรนด์จริงโดยไม่มี decision ของ HUMAN" และเป็นความเสี่ยงลิขสิทธิ์ตรง ๆ) วิธีทำให้ปลอดภัย: สังเคราะห์เสียงเองด้วย oscillator/noise สั้น ไม่ sample เสียงจริงจากที่ไหน, ตั้ง interval ของโน้ต (ถ้ามี) ให้ต่างจากเสียงระฆัง BTS จริงอย่างน้อย 1 คู่เสียง (ไม่ใช่ minor third เดียวกัน), ไม่ใช้ชื่อไฟล์หรือ comment ที่อ้างถึงแบรนด์จริง

**สิ่งที่ห้ามเด็ดขาด (เข้ากับข้อห้าม art direction เรื่อง rarity/enhance):**
- ห้ามเสียง slot machine, เหรียญร่วง, เสียงไฟลุกวาบ หรือเสียง "jackpot" กับ enhance/drop ไม่ว่าระดับใด (ตรงกับที่ art direction ห้าม imagery slot/fire บน enhance)
- ห้ามเสียงระฆังวัด, เสียงสวดมนต์, หรือเสียงที่อ้างอิงศาสนสถาน (P5 ห้ามแตะศาสนา)
- ห้ามเสียงพากย์ตัวละคร (voice acting) ใน v1 — ทุกอย่างเป็น non-verbal cue หรือ UI beep เท่านั้น เพื่อไม่ผูกกับภาษาใดภาษาหนึ่งและประหยัดขนาดไฟล์

## 5. Loudness target และ peak

- **เสียง one-shot/stinger ทั้งหมด (ทุก cue ในเอกสารนี้):** normalize ให้ loudness เฉลี่ยระยะสั้น (short-term) อยู่ที่ **-16 LUFS ± 1 LU** และ **true peak ไม่เกิน -1 dBTP** — ใช้มาตรฐานเดียวกับที่เพลงทั่วไปใช้ (EBU R128) แม้ cue จะสั้นกว่าเพลงมาก เพื่อให้ทุกไฟล์ที่ render จาก generator ต่างกันดังใกล้เคียงกันโดยไม่ต้อง mix ทีละไฟล์ด้วยมือ
- **ลำดับความดังสัมพัทธ์ระหว่าง cue** (สำคัญกว่าค่าสัมบูรณ์ เพราะสุดท้ายเสียงต้องแข่งกับถนน): tickDenied (เบาสุด, ตั้งใจให้จางกว่า tickGranted ตาม flow §4.6) < tickGranted/drop common < dungeon enter/party < hpLow < raid checkpoint < autoRetreat < death (ดังสุด เพราะเกิดไม่บ่อยและต้องรู้ทันที) — ปรับด้วย gain stage ในตัว generator ไม่ใช่ปรับที่ระบบเล่นเสียงฝั่ง client
- **ไม่มีเพลงประกอบ** จึงไม่มีค่า integrated LUFS ระดับเพลงให้กำหนด (ดูหัวข้อ 1 ข้อ 2) ถ้า HUMAN ตัดสินใจใส่เพลงจริงในอนาคต ใช้ -16 LUFS integrated / -1 dBTP เป็นค่าตั้งต้นเดียวกัน

## 6. กฎ mix และ ducking กับเสียงรถและคนรอบตัว

โจทย์: ผู้เล่นได้ยิน cue ท่ามกลางเสียงรถ (low-frequency rumble, แตร), เสียงคนคุย (300 Hz–3 kHz ทับซ้อนกับเสียงพูด), และลำโพงมือถือที่ตอบสนองความถี่ต่ำได้แย่

1. **เน้นย่านกลาง-สูง 800 Hz–3.5 kHz** ทุก cue — ตัด/ลดพลังงานต่ำกว่า 300 Hz ด้วย high-pass filter เพราะลำโพงมือถือเล็กเล่นความถี่ต่ำไม่ออกอยู่แล้วและมันไปแข่งกับเสียงรถเปล่า ๆ
2. **transient เร็ว (attack < 10 ms)** ทุก cue เพื่อให้หูจับ "จุดเริ่ม" ได้แม้ท่ามกลางเสียงรบกวนต่อเนื่อง — ไม่ใช้ fade-in
3. **ไม่มีเสียงพื้นหลัง (ambient bed) ให้ duck** เพราะ v1 ไม่มีเพลง/ambient loop (หัวข้อ 1, 4) จึงไม่ต้องมี sidechain ducking ระหว่าง cue กับเพลงพื้นหลัง — ประเด็น ducking เดียวที่มีจริงคือ **ห้าม cue สองอันซ้อนกันจนฟังไม่ออก**: ถ้า cue ใหม่มี priority สูงกว่ากำลังเล่นอยู่ (ตาราง priority ใน cue-list) ให้ตัดเสียงเดิมทันทีแล้วเล่นตัวใหม่ (hard cut ไม่ crossfade เพราะ cue สั้นอยู่แล้ว) ถ้า priority เท่ากันหรือต่ำกว่า ให้เข้าคิวเล่นถัดไปหรือทิ้งถ้าห่างจาก event เกิน 2 วินาที (ไม่มีประโยชน์แล้ว)
4. **mono-compatible เสมอ** ไม่ pan ซ้าย-ขวา เพราะโทรศัพท์อยู่ในกระเป๋าหรือมือเดียว ลำโพงมักออกทางเดียว การ pan จะทำให้บาง cue หายไปครึ่งหนึ่ง
5. **ไม่พึ่งความดังอย่างเดียวเพื่อ "ชนะ" เสียงถนน** เพราะดันความดังเกิน -1 dBTP จะทำให้เสียงแตกและน่ารำคาญยิ่งกว่าเดิม ให้พึ่งการเลือกความถี่ (ข้อ 1) และจังหวะ transient (ข้อ 2) แทนตาม principle ของการ mix กลางเสียงรบกวน ("cut through", ไม่ใช่ "ดังกว่า")

## 7. วิธีออกแบบสั่นก่อนเสียง (vibration-first) และระดับความเร่งด่วน

ขั้นตอนที่ใช้กับ cue สำคัญทุกตัว (ตรงตามกฎที่ role ต้องทำ): (1) ตั้งคำถามว่าอาการนี้ควร "รู้สึก" อย่างไรถ้าโทรศัพท์อยู่ในกระเป๋ากางเกง (2) ออกแบบ `pattern` (ms array ของ `navigator.vibrate()`) ให้ความยาว/จังหวะ/จำนวนจังหวะแตกต่างจากอันอื่นจนแยกได้โดยไม่ต้องนับ (3) ค่อยแต่งเสียงให้ตรงจังหวะเคาะเดียวกับ pattern สั่น ไม่ใช่คนละจังหวะ

**ระดับความเร่งด่วน 4 ชั้น** (จากเบาไปหนัก จำนวนจังหวะและความยาวรวมเพิ่มขึ้นตามลำดับ เพื่อให้ "รู้สึกหนักขึ้น" ได้แม้แยกความหมายที่แท้จริงไม่ออกในครั้งแรกที่เจอ):

| ชั้น | ใช้กับ | ลักษณะ pattern | ความยาวรวมสูงสุด |
| --- | --- | --- | --- |
| **นุ่ม (soft)** | tickDenied, tap feedback ทั่วไป | จังหวะเดียว สั้นมาก | ≤ 30 ms |
| **ปกติ (normal)** | tickGranted, dungeon enter, drop common/uncommon | 1–2 จังหวะ | ≤ 150 ms |
| **เตือน (warning)** | HP 30%, raid checkpoint, raid 30 นาทีสุดท้าย | 3 จังหวะ จังหวะเว้นเท่ากัน (อ่านออกว่า "เตือน" ไม่ใช่ "ยินดี") | ≤ 400 ms |
| **วิกฤต (critical)** | auto-retreat, ตาย | 3–4 จังหวะ จบด้วยจังหวะยาวสุดท้าย (อ่านออกว่า "จบแล้ว") | ≤ 900 ms |

ตัวเลข pattern จริงของแต่ละ cue อยู่ใน `audio/cue-list.md` (คอลัมน์ `vibration_ms`) — ห้ามใช้ pattern เดียวกันซ้ำระหว่าง 2 cue ที่อยู่ต่างชั้นความเร่งด่วนกัน แม้จะคล้ายกันในชั้นเดียวกันได้ (เช่น tickGranted กับ dungeon enter คล้ายกันได้เพราะทั้งคู่เป็นเรื่องดี ไม่ต้องแยกขาดจากกัน)

**งบแบต:** ทุก pattern เป็น one-shot ไม่วน (ไม่มี `setInterval` เรียกซ้ำ) ความยาวรวมทุก cue ไม่เกิน 900 ms ตามตารางข้างต้น เพื่อไม่ให้มอเตอร์สั่นทำงานถี่จนกินแบตระหว่าง raid ที่ยาว 2 ชั่วโมง

## 8. กฎ rarity ต้องไม่พึ่งเสียงอย่างเดียว

ตรงกับ art direction (`icon-grammar.md` หัวข้อ 4): rarity มี 4 ช่องทาง visual (สี, จำนวน pip, ความหนา/ชั้นขอบ, มุมตกแต่ง) อยู่แล้วโดยไม่พึ่งเสียง เสียง/สั่นของ drop จึงเป็น **ช่องทางที่ 5 แบบเสริม ไม่ใช่ช่องทางบังคับ**:

- cue ของ drop **ต่อยอดจาก** cue ของ `run.tickGranted` เสมอ ไม่ใช่ cue แยกที่มาแทนที่ (ผู้เล่นไม่มีทางพลาด tickGranted เพราะเกิดทุก reward tick อยู่แล้ว ส่วน layer ของ rarity เป็นแค่ "หาง" ต่อจากมัน)
- ยิ่ง rarity สูง ยิ่งมีจำนวนจังหวะ/โน้ตมากขึ้นแบบขั้นบันได (ดูตารางใน cue-list) แต่ **ไม่ใช้เสียงหมุน วน หรือ build-up ก่อนเฉลย** แบบสล็อต (ต้องรู้ผลทันทีที่ระบบรู้ผล ไม่ delay เพื่อสร้าง suspense เทียม — ตรงกับ "ห้าม imagery slot/fire" ของ art direction และหลักการเกม server-authoritative ที่ผลถูกตัดสินที่ server แล้วก่อนแสดงผลด้วยซ้ำ)
- ถ้าอุปกรณ์ไม่รองรับ `navigator.vibrate()` (ดูหัวข้อ 2) หรือเสียงถูกปิด ผู้เล่นยังทราบ rarity ได้ครบจากภาพเพียงอย่างเดียวเสมอ — ไม่มีสถานการณ์ใดที่ต้องได้ยินเสียงถึงจะรู้ rarity

## 9. โทนของ enhance (คอมเมดี้ ไม่ใช่โศกนาฏกรรม, ห้าม slot-machine)

ของไม่มีวันแตกเมื่อตีบวก (`config: enhance.rules.itemCanBreak = false`, N-5) ผลลัพธ์ที่แย่ที่สุดคือ "เสียวัตถุดิบ" หรือ "อุปกรณ์ลดระดับ" (`config: enhance.failureOutcomeByTargetLevel`) ไม่ใช่การสูญเสียถาวรของตัวไอเทม — โทนเสียงจึงต้อง **ล้อกับความจริงว่านี่คือ gold sink ที่ตั้งใจ ไม่ใช่โศกนาฏกรรม**:

- **สำเร็จ:** เสียงสั้นแบบเดียวกับ tickGranted แต่เด่นกว่าเล็กน้อย (นี่เป็นการตัดสินใจที่ผู้เล่นลงทุนเอง ควรรู้สึกดีกว่าการได้ของแบบ passive)
- **ล้มเหลว (materialsLost/dropOneLevel):** โทน "เครื่องคิดเลขร้านทอง" หรือ "ตู้ ATM ตัดเงิน" — เสียง click/beep แห้ง ๆ สั้น ๆ ให้ความรู้สึก "หักเงินไปแล้วนะ" แบบตรงไปตรงมา ไม่ใช่เสียงระเบิด ไม่ใช่เสียงแก้วแตก ไม่ใช่เสียงร้องของตัวละคร — ตรงกับ pillars P5 "ระบบที่ดูดเงินพูดตรง ๆ ว่าดูดเงิน"
- **ห้ามเด็ดขาด:** เสียงหมุนสล็อต, เสียงเหรียญไหลรัว, เสียงไฟลุก/พลุ, เสียง fanfare ยาวเกิน 600 ms สำหรับผลตีบวกเดียว (แม้จะสำเร็จ) เพราะกระตุ้นพฤติกรรมแบบพนัน
- **หมายเหตุขอบเขต:** enhance ยังไม่มี copy key ใน `config/content/copy.th.json` ปัจจุบัน (เป็นของ feature ตีบวกใน phase ถัดไป ไม่ใช่ F03 core loop) หัวข้อนี้เป็นทิศทางล่วงหน้าเพื่อกันหลุดโทนเท่านั้น cue id จริงใน cue-list ทำเครื่องหมาย "ชั่วคราว รอ copy key" ไว้ชัดเจน

## 10. Silent-mode และ fallback philosophy

เว็บไม่มี API ที่เชื่อถือได้ในการรู้ว่าเครื่องอยู่ในโหมดปิดเสียงหรือไม่ (หัวข้อ 2) หลักการจึงไม่ใช่ "ตรวจสอบแล้วสลับไปสั่นแทน" แต่เป็น **ยิงทุกชั้นพร้อมกันเสมอ แล้วให้แต่ละชั้นทำงานอิสระ**:

1. **Visual** (toast/banner ตาม copy key ที่มีอยู่แล้วใน UX flow) — เป็นชั้นเดียวที่การันตีว่าทำงานเสมอ (มีอยู่แล้วในทุก beat ตาม `F03-core-loop.md`)
2. **Vibration** (ถ้า platform รองรับ, Android เป็นหลัก) — ยิงพร้อม visual ทันที ไม่รอเสียง
3. **Sound** (ถ้าไม่ถูกปิดเสียง/ไม่โดน autoplay policy บล็อก) — ยิงพร้อมกัน เป็นชั้นเสริมความรู้สึก ไม่ใช่ชั้นที่ข้อมูลสำคัญพึ่งพา
4. **Push notification** (เฉพาะตอนแอปอยู่เบื้องหลัง/จอดับ) — ใช้ copy key เดียวกับ toast (ตาม `F03-core-loop.md` §8) เสียง/สั่นของ push เป็นของ OS ควบคุมไม่ได้จากโค้ดเรา และ **ไม่ได้ใช้ pattern ที่ออกแบบในเอกสารนี้**

ผลคือ: ไม่มี cue ใดในเกมที่ "ต้องได้ยิน" หรือ "ต้องรู้สึกสั่น" ถึงจะเข้าใจ — ทุกอย่างอ่านได้จาก visual เป็น baseline เสมอ เสียง/สั่นมีไว้เพื่อให้รู้ **เร็วกว่า** การหยิบมือถือขึ้นมาดู ไม่ใช่เพื่อให้รู้ **ได้เท่านั้น**
